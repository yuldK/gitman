# 단계 3 `S3-D4-CODE` 검증 기록 - 2026-08-16

## 1. 결과

timeout, 취소와 job object 기반 트리 종료를 구현했다. 제한 시간이나 취소로 끝난 실행은 자식과 손자 프로세스를 함께 정리하고, reader 스레드는 어떤 경로에서도 `run` 반환 전에 join된다.

VS2022 Debug/Release와 VS2026 Debug build가 통과했고 기존 전체 CTest가 각 118/118 통과했다. VS2022 `/analyze`는 경고 없이 통과했다. 새 test source는 작성하지 않았고, 저장소 밖 임시 프로그램으로 19개 항목을 수동 확인했다. 상세는 5장에 있다.

## 2. 구현 범위

### 2.1 취소 전 확인

`run`은 프로세스를 만들기 전에 token 상태를 먼저 본다. 이미 취소된 요청은 `cancelled`와 `process_cancelled` 진단만 반환하고 자식을 시작하지 않는다. 대기열에 오래 남아 있던 작업이 뒤늦게 실행되는 것을 막는다.

### 2.2 job object와 정지 시작

| 항목 | 구현 |
| --- | --- |
| job 생성 | `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`를 설정한 job을 만든다. handle이 닫히면 남은 프로세스가 정리되므로 예외 경로에서도 orphan이 남지 않는다. |
| 정지 시작 | `CREATE_SUSPENDED`로 시작한다. job에 넣기 전에 자식이 손자를 만들면 그 손자가 job 밖에 남기 때문이다. |
| job 배정 | `AssignProcessToJobObject` 후 `ResumeThread`로 자식을 재개한다. |
| 재개 실패 | 정지 상태의 자식을 정리하고 `start_failed`로 반환한다. |
| job 사용 불가 | job을 만들거나 배정하지 못해도 실행을 계속하되 warning 진단을 남기고 종료 범위를 자식 하나로 줄인다. 제한된 환경에서 실행 자체가 막히지 않게 한 선택이다. |

### 2.3 timeout과 취소 대기

- 취소 token에 콜백을 등록해 event 하나를 신호한다. polling이 없고 Win32 type도 상위 계층에 노출되지 않는다.
- event handle을 registration보다 먼저 선언해 registration이 항상 먼저 해제되게 했다. 콜백이 이미 닫힌 event를 신호하는 일이 없다.
- `WaitForMultipleObjects`로 프로세스 handle과 취소 event를 함께 기다리며 timeout을 적용한다. timeout이 없으면 `INFINITE`다.
- `std::chrono::milliseconds` 값이 `INFINITE`와 겹치지 않도록 상한을 둔다.
- 자식이 스스로 끝난 경우가 아니면 트리를 종료한다. 종료하면 pipe가 닫혀 reader 스레드가 EOF를 보고 끝나므로 join이 지연되지 않는다.

### 2.4 결과 판정

| 대기 결과 | 완료 사유 | 종료 코드 |
| --- | --- | --- |
| 프로세스 신호 | `exited` | `GetExitCodeProcess` 값 |
| 취소 event 신호 | `cancelled` | 비움 |
| 제한 시간 초과 | `timed_out` | 비움 |
| 대기 실패 | `internal_error` | 비움 |

취소와 timeout은 자식을 강제 종료하므로 종료 코드에 의미가 없다. 그래서 값을 채우지 않고 `succeeded()`도 거짓이 된다. 그때까지 수집한 출력 레코드와 캡처 통계는 그대로 결과에 남는다.

## 5. 저장소 밖 수동 확인

`%TEMP%`에 임시 자식과 확인 프로그램을 만들어 실행하고 삭제했다. 도우미의 `sleep`과 `spawn-child` 명령은 `S3-D4-TEST`에서 저장소에 추가한다.

| 항목 | 결과 |
| --- | --- |
| 10초 자식에 400 ms timeout을 걸면 `timed_out`으로 끝나고 종료 코드가 비어 있으며 성공이 아님 | 통과 (483 ms 만에 반환) |
| timeout 이전에 나온 출력 2줄이 sink에 전달됨 | 통과 |
| 실행 시간이 요청한 timeout 이상으로 측정됨 | 통과 |
| 실행 중 300 ms 뒤 취소하면 `cancelled`로 끝나고 종료 코드가 비어 있음 | 통과 (314 ms 만에 반환) |
| 이미 취소된 token은 프로세스를 시작하지 않고 출력도 없음 | 통과 |
| 손자 프로세스를 만든 자식을 timeout으로 종료하면 손자도 함께 사라짐 | 통과 (marker 파일 미생성) |
| timeout을 넉넉히 준 빠른 자식은 정상 종료 코드를 유지함 | 통과 |
| 취소하지 않은 token은 정상 실행에 영향을 주지 않음 | 통과 |
| 30회 반복 실행 후 프로세스 handle 수가 늘지 않음 | 통과 (78 → 78) |

손자 종료 확인은 손자가 2초 뒤 marker 파일을 만들도록 하고, 부모를 500 ms에 timeout시킨 뒤 3.5초를 기다려 파일이 없는 것으로 판정했다.

## 6. 구현 중 검토 결과

- `CREATE_SUSPENDED` 없이 job에 배정하면 자식이 배정 전에 손자를 만들 수 있고 그 손자는 job 밖에 남는다. 정지 시작과 `ResumeThread`가 이 경쟁을 없앤다.
- job 실패를 치명적 오류로 처리할지 검토했다. 중첩 job이 제한된 환경에서 실행 자체가 불가능해지는 위험이 더 크다고 판단해 warning과 함께 단일 프로세스 종료로 물러선다.
- `KILL_ON_JOB_CLOSE` 덕분에 예상하지 못한 반환 경로에서도 job handle이 닫히면서 자식이 정리된다. `internal_error` 경로의 안전망이 하나 더 늘었다.
- 현재 알려진 production 결함은 없다. 전용 test는 체크포인트 분리 규칙에 따라 아직 작성하지 않았다.
