# 단계 2 `S2-D4-CODE` 검증 기록 - 2026-08-15

## 1. 결과

`.verison-list` 작업공간 문서의 opaque revision token, exact-byte 동시 수정 감지, JSON serialize 및 재검증, Win32 원자적 교체, backup 탐지와 명시적 recovery production code 구현을 완료했다.

VS2022와 VS2026 Debug build 및 기존 전체 CTest 41/41이 모두 통과했다. 이번 체크포인트에서는 새 test source나 fixture를 작성하지 않았다. 사용자가 2026-08-15에 다음 작업 진행을 지시해 코드 검수를 승인했고, 후속 결과는 `docs/verification/2026-08-15-stage-2-d4-test.md`에 기록한다.

## 2. application 계약

| 항목 | 구현 내용 |
| --- | --- |
| revision token | load 당시 primary 존재 상태와 원문 byte, JSON shadow 및 유효 project 원래 index를 caller가 해석할 수 없는 token으로 캡슐화한다. |
| load 결과 | domain document, 구조화 diagnostic, revision token과 primary/backup source만 public type으로 노출한다. |
| save 결과 | 성공 시 새 원문 byte에 대응하는 revision token을 반환해 다음 save가 직전 결과를 기준으로 충돌을 검사하게 한다. |
| recovery 진입 | primary `load`와 명시적 `load_backup`을 분리한다. backup load도 현재 primary revision을 함께 캡처해 복구 save의 충돌을 검사한다. |
| I/O 경계 | read 상태와 atomic commit의 write, flush, replace 실패를 구분하는 작은 file adapter 계약을 둔다. |

public application header에는 nlohmann/json, Win32와 Skia type을 노출하지 않는다.

## 3. JSON store

- primary load는 file read, schema parse와 path resolution을 하나의 store pipeline으로 연결한다.
- primary document-level load 실패에만 같은 디렉터리의 `<document-name>.verison-list.bak`을 검사한다.
- 유효한 backup은 `recovery_available`, 읽을 수 없거나 schema/path 오류가 있는 backup은 `backup_invalid` diagnostic으로 반환하며 자동 적용하지 않는다.
- 명시적 backup load는 backup을 parse 및 path resolve한 뒤 target document path를 primary로 유지한다.
- save는 shadow JSON의 unknown top-level 및 project field를 보존하고 domain 값으로 알려진 field를 갱신한다.
- 생략됐던 optional field가 기본값 그대로이면 임의로 추가하지 않으며, 사용자가 입력한 `path.original`만 serialize한다.
- 저장 byte는 UTF-8 무 BOM, 공백 4칸, CRLF와 마지막 줄 끝을 사용한다.
- serialize 결과를 schema parser와 path resolver로 전체 재검증하고 error가 하나라도 있으면 file adapter를 호출하지 않는다.
- 재검증 뒤 primary 현재 byte를 revision token의 load 당시 byte와 정확히 비교한다. 존재 상태 또는 byte가 다르면 `concurrent_modification`으로 실패한다.

## 4. Win32 원자적 저장

- UTF-8 document 및 backup path를 UTF-16 absolute extended-length path로 변환하고 device namespace는 거부한다.
- target과 같은 디렉터리에 process ID와 sequence를 사용한 충돌 없는 임시 파일을 `CREATE_NEW`로 만든다.
- 임시 파일 전체 write 뒤 `FlushFileBuffers`를 호출하고 handle을 닫은 후에만 교체한다.
- 기존 target은 `ReplaceFileW`로 교체하면서 `<document-path>.bak`에 직전 원본을 남긴다.
- 최초 생성은 `MOVEFILE_WRITE_THROUGH`를 사용하고 기존 파일을 덮어쓰는 flag를 사용하지 않는다.
- write, flush 또는 replace 실패에서는 임시 파일을 정리한다. `ERROR_UNABLE_TO_MOVE_REPLACEMENT_2`로 원본이 backup 이름으로 이동한 부분 실패는 primary 이름 복원을 시도하며, 복원이 불가능해도 원본 byte는 backup에 남는다.
- 성공 뒤 결과 조립 중 allocation 실패가 저장 성공을 실패로 오인하지 않도록 다음 revision token을 commit 전에 준비한다.

## 7. 구현 중 검토 결과

Win32 `ReplaceFileW`의 write-through flag는 공식 API에서 지원되지 않으므로 승인된 계획대로 temp data의 `FlushFileBuffers`를 먼저 완료하고 flags `0`으로 교체한다. 최초 생성에는 지원되는 `MOVEFILE_WRITE_THROUGH`를 적용했다. `ReplaceFileW`의 문서화된 부분 실패에서 원본이 backup 이름으로 이동할 수 있어 primary 복원 경로도 포함했다.

현재 알려진 미수정 production 결함은 없다.

## 8. 검수 완료

사용자가 2026-08-15에 다음 작업 진행을 지시해 `S2-D4-CODE`를 승인했다. 이에 따라 `S2-D4-TEST`에서만 다음 test를 추가했다.

- 최초 생성과 기존 file 교체, UTF-8 무 BOM, 4칸 및 CRLF 출력
- load 뒤 external byte 변경의 무수정 실패
- write, flush와 replace 실패 주입 및 기존 byte와 temp 정리 확인
- 직전 원본 backup, valid/invalid backup 탐지와 명시적 backup load
- unknown field와 원문 path round-trip 보존

test가 production 결함을 드러내더라도 같은 체크포인트에서 production source를 수정하지 않고 `S2-D4-FIX` 검수 대상으로 기록하는 제한을 유지했다. 실제 test 결과 production 결함은 발견되지 않았다.
