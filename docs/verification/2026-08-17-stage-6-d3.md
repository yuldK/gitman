### 2.1 핵심 결정

- **lane = 안정 hash(project id) % worker 수.** 같은 카드는 항상 같은 worker의 MPSC inbox로 가므로 카드별 직렬화가 FIFO 소비로 저절로 보장된다(ADR-005의 MPMC 없는 분배). 문서 load는 항상 0번 lane이다. 전체 동시 상한은 worker 수다(계획 4.4).
- **event는 유실하지 않는다.** logic inbox가 가득 차면 1ms 물러났다 재시도하고, 닫힌 inbox(종료 중)로 가는 event만 조용히 버린다(ADR-005 7.3). channel의 post가 값을 소비하므로 재시도는 사본으로 한다.
- **shutdown은 inbox close → join이다.** 남은 요청은 취소된 token과 함께 빠르게 소진된다. 멱등이고 소멸자에서도 호출된다.
- executor는 **어떤 실패에서도 final event를 보낸다.** logic의 busy가 마지막 event로만 풀리기 때문이다.
- automatic 카드의 provider 선택은 **단계 5의 표식 판정을 재사용**한다. 프로세스 없이 종류만 정하고 정확한 상태는 provider가 판정한다. 표식이 없으면 Git provider가 `not_a_repository`를 그대로 보고한다.
- 도구 조사는 settings 값 기준으로 cache해 매 조회마다 `--version`을 실행하지 않는다(단계 4 registry 정책의 계승). 조사는 잠금 밖에서 하고 결과 등록만 잠근다.

## 3. test 범위

- scheduler 6개: lane 결정성과 상한, **단일 worker의 접수 순서 실행과 동시 실행 없음(peak 1)**, **다른 lane 두 개의 실제 병렬(peak 2, 직렬이면 5초 timeout으로 실패)**, logic inbox로의 event 도달, 문서 load의 0번 lane, shutdown 후 제출 거부와 멱등성
- executor 5개: store 경유 문서 load(진단 승격 포함), 도구 없는 Git 카드의 `tool_unavailable`과 **프로세스 0개**, automatic의 표식 기반 provider 선택(.svn→SVN, .git→Git), refresh의 로컬(final=false)→원격(final=true) 순서와 generation echo, settings 지정 경로의 cache 동작

모든 test가 실제 VCS 프로세스 없이 fake runner·probe·store로 결정적으로 실행된다. 실제 provider 동작은 단계 4가 이미 검증했다.
