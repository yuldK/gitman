# 단계 4 `S4-D2-CODE` 검증 기록 - 2026-08-16

## 1. 결과

Git 로컬 조회 경로를 구현했다. 명령 조립(`rev-parse`, `status --porcelain=v2`), 출력 파서, 진행 중 작업 표식 probe와 공통 `repository_snapshot` 변환까지다.

### 2.3 `-z` 사용 여부 확정

계획 4.4와 4.10은 `status --porcelain=v2 -z`를 전제하고, NUL 구분 출력을 손상 없이 받는 방법을 이 구간에서 확정하기로 남겼다. **확정 결과는 `-z`를 사용하지 않는 것이다.**

단계 3의 출력 파이프라인은 줄 단위 레코드를 만들면서 줄 끝 문자를 레코드에 남기지 않는다. 따라서 `-z` 출력은 파이프라인을 통과하는 순간 다음 문제가 생긴다.

- NUL만으로 구분된 출력에는 줄 끝이 없어 레코드가 캡처 상한이나 레코드 상한에서만 끊긴다.
- 경로에 `\n`이나 `\r`이 들어가면 파이프라인이 그 자리를 레코드 경계로 보고 문자를 버린다. `-z`를 고른 이유였던 "개행이 든 경로"가 오히려 손상된다.
- 로그 뷰(단계 7)에 NUL이 가득한 한 줄이 남는다.

반대로 줄 단위 출력에서는 Git이 제어 문자, `"`와 `\`가 들어간 경로를 C 인용으로 감싸므로 줄 경계가 흔들리지 않는다. `core.quotepath=false`는 비ASCII를 8진 이스케이프하지 않게 할 뿐 이 인용 자체를 없애지 않는다는 것을 호스트의 Git 2.52.0으로 확인했다. 인용 해제는 `unquote_git_path`가 담당한다.

이 선택으로 단계 3 코드는 그대로 두고, 원시 byte sink도 추가하지 않는다.

다만 rename 레코드는 한 줄에 경로 두 개를 담아 기본 레코드 상한 8 KiB를 넘을 여지가 있다. 끊긴 줄은 파서가 다른 레코드로 오해하므로 `status` 명령에만 64 KiB 상한을 준다. 이를 위해 `make_vcs_process_request`에 기본 인자를 하나 추가했고 기존 호출자는 그대로 컴파일된다.

### 2.4 저장소 배치 판정 (계획 11장 미결정 항목)

`rev-parse` 인자 순서를 다음으로 고정했다. 출력 순서가 곧 이 순서다.

```text
rev-parse --absolute-git-dir --is-bare-repository --is-inside-work-tree --show-toplevel
```

`--show-toplevel`은 bare 저장소와 git dir 안에서 실패한다. Git은 인자를 순서대로 처리하고 실패 전까지의 값은 이미 출력하므로, 이 인자를 마지막에 두면 실패한 경우에도 앞의 세 값으로 배치를 판정할 수 있다. 호스트에서 실측한 동작이다.

| 관측 | 판정 |
| --- | --- |
| 출력 없음, 프로세스는 정상 종료 | `not_a_repository`. 로캘과 무관한 구조적 신호다. 번역되는 `fatal: not a git repository` 문장으로 판정하지 않는다. |
| 프로세스가 timeout, 취소, 시작 실패 | `unknown`. 단계 3의 완료 사유를 그대로 승격한다. |
| `is-bare-repository`가 참 | `unsupported_layout` |
| `is-inside-work-tree`가 거짓 (git dir 안의 경로) | `unsupported_layout` |
| linked worktree | 정상 조회. git dir이 `<main>/.git/worktrees/<name>`이고 진행 중 작업 표식도 그 디렉터리에 있어 추가 처리가 필요 없다. |

`repository_availability::unsupported_layout`을 새로 넣었다. bare 저장소를 `not_a_repository`로 보고하면 카드에 잘못된 사유가 뜬다. 지원 범위 자체는 계획대로 단계 5에서 정하고, 단계 4는 이 상태를 미설치·잘못된 경로와 구분해 보고만 한다.

### 2.5 로컬 상태 조회

```text
git -c core.quotepath=false -c gc.auto=0 -c color.ui=false --no-pager status --porcelain=v2 --branch --untracked-files=normal --ignored=no
```

`--ignored=no`는 기본값이지만 Git 설정으로 바뀌지 않도록 명시했다. `--branch` 헤더에서 `branch.oid`, `branch.head`, `branch.upstream`, `branch.ab`를 읽고, 알 수 없는 헤더(`# stash 1` 등)는 무시한다. Git이 헤더를 추가해도 기존 판정이 깨지지 않아야 하기 때문이다.

| porcelain v2 레코드 | 처리 |
| --- | --- |
| `1`, `2` | XY 중 하나라도 비`.`이면 `modified_count` 증가. `2`는 `<path><TAB><원래 경로>` |
| `u` | `conflicted_count` 증가 |
| `?` | `untracked_count` 증가 |
| `!` | 세지 않는다 |
| 그 외 | `unparsable_records` 증가 |

`working_tree_state`는 충돌이 있으면 `conflicted`, 아니면 변경이나 untracked가 있으면 `modified`, 둘 다 없으면 `clean`이다. untracked만 있는 경우도 `modified`이며 개수는 따로 남긴다.

**해석하지 못한 레코드가 있거나 branch 헤더를 찾지 못하면 상태를 `unknown`으로 둔다.** 출력을 다 읽지 못한 저장소를 깨끗하다고 보고하면 보호 정책이 위험한 저장소에서 변경 명령을 허용하게 된다. `is_safe_for_change()`가 `unknown`을 안전으로 보지 않는 것과 같은 방향이다.

### 2.6 진행 중 작업 표식

Git에는 진행 중 작업을 알려 주는 기계 판독 명령이 없다. `vcs_file_probe`로 git dir 안의 표식을 확인한다.

| 표식 | 종류 | 결과 |
| --- | --- | --- |
| `MERGE_HEAD` | 파일 | merge |
| `rebase-merge`, `rebase-apply` | 디렉터리 | rebase |
| `CHERRY_PICK_HEAD` | 파일 | cherry-pick |
| `REVERT_HEAD` | 파일 | revert |
| `BISECT_LOG` | 파일 | bisect |
| `index.lock` | 파일 | 다른 Git 프로세스가 작업 중 |

`index.lock`은 `operation_in_progress()`에 넣지 않고 `has_index_lock`으로 따로 보고한다. 중단된 작업이 아니라 지금 다른 프로세스가 도는 상태이므로 사용자가 할 일이 다르다. 보호 정책은 두 경우를 모두 막는다.

### 2.7 snapshot 변환

| 값 | 채우는 방법 |
| --- | --- |
| `repository_root` | `--show-toplevel` |
| `current_reference` | branch 이름. detached면 `(detached) <짧은 커밋 ID>` |
| `local_revision` | `branch.oid`. 커밋이 없는 저장소(`(initial)`)에서는 비운다 |
| `working_tree` | 2.5의 요약 + 2.6의 표식 |
| `local_checked_at` | 조회 시각 |

upstream이 있으면 `comparison`을 `local`, `comparison_target`을 upstream 이름으로 채우고 `branch.ab`로 `sync_state`를 정한다. 이는 **이미 받아 둔 remote tracking ref와의 비교**이며 네트워크를 쓰지 않는다. `comparison_source::local`이 그 사실을 나타낸다. 원격을 실제로 확인하는 remote-first 판정은 `S4-D3`의 `query_remote`가 덮어쓴다.

로컬 조회만으로 `local_only`나 `remote_target_missing`을 판정하지 않는다. 두 값은 `git remote` 결과가 있어야 구분되며 `S4-D3` 범위다. upstream이 없으면 `sync_state`는 `unknown`으로 남는다.

### 2.8 경로 확인 순서

명령을 만들기 전에 등록 경로가 절대 경로인지 확인하고, 이어서 `vcs_file_probe`로 디렉터리인지 확인한다. 두 경우 모두 실패하면 프로세스를 만들지 않고 각각 `path_unavailable`로 보고한다. 프로세스를 띄워 시작 실패로 알아내는 것보다 사유가 정확하고, 단계 2가 기록한 경로 상태는 오래됐을 수 있다.

## 3. 계획과 다른 점

1. `status --porcelain=v2`에 `-z`를 쓰지 않는다. 근거는 2.3이다.
2. `repository_availability::unsupported_layout`을 도메인에 추가했다. 도메인 확장은 원래 `S4-D1-CODE` 범위였으나, bare 저장소 보고 방식은 계획 11장이 이 구간에서 정하라고 남긴 항목이라 여기서 처리했다.
3. `make_vcs_process_request`에 `maximum_record_bytes` 기본 인자를 추가했다. `S4-D1-CODE`의 파일을 건드리지만 기본값이 기존 동작과 같아 기존 호출자와 test는 영향을 받지 않는다.
4. `git_repository_provider`가 `repository_provider` 계약을 이미 구현한다. 아직 구현하지 않은 네 동작은 명령을 만들지 않고 중립 값을 돌려준다(`executed == false`). 나머지 구간에서 본문만 채운다.
5. 진행 중 작업 판정을 별도 파일로 두지 않고 `git_repository_provider.h`의 자유 함수 `detect_git_in_progress_markers`로 공개했다. 계획 5장의 파일 목록에 없는 파일을 늘리지 않으면서 단독으로 test할 수 있다.
6. 로컬 조회가 `branch.ab`로 `sync_state`를 채운다. 원격 판정 자체는 `S4-D3` 범위지만, 이미 가진 값을 버리면 시작 직후 카드가 아무 상태도 보여 줄 수 없다. 근거를 `comparison_source::local`로 남겨 remote-first 판정과 구분한다.
