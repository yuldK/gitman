## 3. 테스트 도우미

`tests/helpers/vcs_test_doubles.h/.cpp`를 추가했다.

- `fake_process_runner`는 받은 `process_request`를 **그대로 기록**하고 미리 등록한 출력을 돌려준다. "이 조건에서 어떤 명령을 만들었는가"와 "이 출력에서 어떤 값으로 변환했는가"를 한 test에서 함께 단정할 수 있다. 출력은 단계 3 파이프라인과 같은 규칙으로 줄 단위 레코드로 나눠 sink에 전달한다.
- `fake_vcs_file_probe`는 등록한 경로만 존재하는 filesystem 대역이다. Windows 경로 비교와 같게 ASCII 대소문자와 구분자 종류를 무시한다.

계획 5장은 도우미 이름을 `helpers/fake_process_runner.*`로 적었지만 probe 대역까지 함께 담으므로 `helpers/vcs_test_doubles.*`로 정했다. `gitman_tests`에 `${GITMAN_TEST_DIRECTORY}` include 경로와 `gitman_vcs` 링크를 추가했다.

## 4. 사용자 지시 사항의 검증

### 4.1 모든 VCS가 없는 환경

지시하신 "모든 VCS가 없는 경우"를 전용 test로 고정했다.

| 단정 | 내용 |
| --- | --- |
| 빈 probe에서 두 도구 모두 `not_found` | 실행 파일이 없으면 프로세스를 **하나도** 만들지 않는다 (`request_count() == 0`) |
| `none_available()` 참, `any_available()` 거짓 | 전체 비활성화를 한 값으로 판단할 수 있다 |
| 진단 2개가 **모두 warning** | 오류 상태가 아니므로 앱을 멈추지 않는다 |
| `available(repository_kind::unknown)` 거짓 | 종류를 지정하지 않은 조회는 "하나라도 있는가"로 답한다 |

한쪽만 없는 경우도 함께 고정했다. Git만 있는 현재 호스트 구성에서 `any_available()`이 참이고 SVN 카드만 비활성화되며 진단이 1개만 나온다.

조사 전 registry는 진단을 내지 않는다는 것도 단정했다. 조사하기 전에 "도구 없음" 경고를 띄우면 안 되기 때문이다.

### 4.2 로캘 미강제와 오류 분류

같은 실패의 **영어 출력과 한국어 출력이 같은 분류를 내는지**를 `require_same_classification` 도우미로 확인한다. 다음 쌍을 고정했다.

- ssh `Permission denied (publickey)` + 한국어 `치명적: 리모트 저장소에서 읽을 수 없습니다`
- HTTP 401/403의 영어 문장과 한국어 문장
- libcurl `Could not resolve host` + 한국어 감싸는 문장
- 서버가 준 `remote: Repository not found.` + 한국어 감싸는 문장
- SVN `E170013`/`E215004`/`E155007`의 영어와 한국어 메시지

오탐 방지 규칙도 고정했다. `issue-403`, `branch 404`, `error: 4031`, `error: 1401`은 모두 `command_failed`다. HTTP 문맥이 있어야 하고 앞뒤가 숫자가 아닌 독립 토큰이어야 인정한다.

프로세스 결과가 stderr 검사보다 우선한다는 것도 확인했다. timeout으로 끝난 실행에 인증 메시지가 남아 있어도 `timed_out`이다.

`vcs_execution_policy_tests.cpp`는 `LC_ALL`, `LANG`, `LANGUAGE` override가 **없음**을 단정하고, 모든 명령의 인코딩 모드가 `active_code_page_fallback`임을 확인한다.

### 4.3 문서 `settings`

- `workspace-settings.verison-list` fixture로 정상 parse와 알 수 없는 키 warning(`/settings/future~1option~0v2`)을 확인한다.
- 기존 fixture(`valid-complete`, `unknown-fields`)가 그대로 열리고 `settings.is_default()`가 참임을 확인해 **스키마 회귀가 없음**을 고정했다.
- `"settings": null`은 값 없음이며 경고를 만들지 않는다.
- 상대 경로는 `vcs_tool_path_invalid` 오류이고 거부한 값은 문서에 남기지 않는다. UNC 경로는 통과한다.
- 저장 round-trip에서 알 수 없는 키가 보존되고, 기본값만 있는 문서에는 `settings` 필드를 만들지 않으며, 값이 생기면 새로 쓴다.
- 저장 직전 재검증이 상대 경로를 걸러내 손상된 문서가 디스크에 남지 않는 것을 확인했다(`atomic_commit_count() == 0`).

### 4.4 지정 경로가 자동 탐색을 대체함

`PATH` 위치에 사용 가능한 Git이 있는 상태에서 다음 세 경우 모두 `path_invalid`이며 자동 탐색으로 물러서지 않는다.

| 경우 | 확인 |
| --- | --- |
| 상대 경로 지정 | 실행 자체를 시도하지 않는다 (`request_count() == 0`) |
| 지정 경로 없음 | 실행을 시도하지 않고 지정 경로를 결과에 남긴다 |
| 지정 경로가 시작 실패 | 지정 경로로 한 번만 실행하고, 자동 탐색이면 `version_unreadable`일 상황을 `path_invalid`로 보고한다 |

## 6. test 작성 중 확인한 사항

- `S4-D1-CODE`의 임시 프로그램에서 기대값을 틀렸던 `PATH` 중복 제거 동작을 이번에 test로 고정했다. `C:\A\`는 `C:\a`의 대소문자 무시 중복으로 제거되고, 후행 구분자만 다른 항목도 같은 항목으로 본다.
- `vcs_tool_candidates`가 `PATH`의 모든 디렉터리에 대해 후보를 만들기 때문에 SVN 디렉터리에서도 `git.exe` 후보가 생긴다. 존재하지 않으면 probe에서 걸러지므로 문제가 없고, 순서 단정으로 이 동작을 명시했다.
- `repository_query_result::has_errors()`가 warning을 오류로 세지 않는 것을 확인했다. 도구 부재가 warning이므로 이 구분이 없으면 VCS 없는 환경의 모든 조회가 오류가 된다.
- 알 수 없는 열거형 값에 대한 이름과 메시지 함수의 fallback 경로를 모두 호출해 `/analyze`가 지적할 수 있는 미처리 분기가 없음을 확인했다.

## 7. 현재 알려진 결함

없다. production source를 수정하지 않았고 `S4-D1-FIX` 후보도 발견하지 않았다.

## 8. 다음 구간

발견 결함이 없으므로 사용자 확인 후 `S4-D1-FIX`를 생략하고 `S4-D2-CODE`로 넘어간다. `S4-D2-CODE`에서는 Git 명령 조립, `rev-parse`와 `status --porcelain=v2` 파서, 진행 중 작업 probe와 로컬 snapshot 변환만 구현한다.
