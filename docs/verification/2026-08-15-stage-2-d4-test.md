# 단계 2 `S2-D4-TEST` 검증 기록 - 2026-08-15

## 1. 결과

`.verison-list` project store와 Win32 file adapter를 대상으로 Catch2 test 9개를 추가했다. 최초 생성과 기존 파일 교체, exact-byte 동시 수정 감지, 저장 후보 재검증, write/flush/replace 실패 진단, canonical JSON 출력, backup 탐지와 명시적 recovery를 검증했다.

VS2022와 VS2026 Debug build 및 전체 CTest 50/50이 모두 통과했다. 이번 체크포인트에서 `src/` production source는 변경하지 않았고, `S2-D4-FIX` 대상으로 기록할 production 결함도 발견하지 않았다. 사용자가 2026-08-16에 진행을 지시해 test 검수를 승인했다.

## 2. 추가한 test 범위

| test | 검증 내용 |
| --- | --- |
| `Project store creates new documents without replacement backups` | missing revision에서 최초 문서를 생성하고 backup 없이 UTF-8 무 BOM, 공백 4칸, CRLF와 마지막 줄 끝을 갖는 canonical JSON을 저장한다. |
| `Project store preserves shadow fields and canonical output` | unknown top-level/project field와 사용자가 입력한 path 원문을 보존하고 변경된 domain field만 반영한다. |
| `Project store rejects stale exact byte revisions` | load 뒤 의미상 같은 JSON이라도 원문 byte가 달라지면 `concurrent_modification`으로 실패하고 commit하지 않는다. |
| `Project store revalidates complete candidates before committing` | serialize된 전체 후보에서 duplicate project ID를 다시 검출하고 file adapter 호출 전에 저장을 중단한다. |
| `Project store maps injected commit failures without changing originals` | fake adapter가 주입한 write, flush와 replace 실패를 개별 diagnostic과 native error로 매핑하고 원본을 보존한다. |
| `Project store reports backups and requires explicit recovery` | 손상 primary를 자동 복구하지 않고 valid backup만 알린 뒤, 명시적 backup load 및 save에서 직전 손상 primary를 새 backup으로 남긴다. |
| `Project store rejects invalid recovery backups` | schema가 잘못된 backup을 recovery 후보로 표시하지 않고 명시적 load도 구조화 오류로 거부한다. |
| `Win32 workspace storage creates replaces and detects external changes` | 실제 임시 디렉터리에서 최초 생성, `ReplaceFileW` 교체, 직전 byte backup, 외부 변경 충돌과 임시 파일 정리를 검증한다. |
| `Win32 workspace storage cleans temporary files after replace failure` | 공유 삭제가 차단된 실제 target에서 replace 실패를 유도하고 원본 byte 보존, backup 미생성과 임시 파일 정리를 검증한다. |

## 3. test 경계와 fixture

- 작은 in-memory file adapter fake가 read 및 atomic commit 계약을 구현하고 write, flush와 replace 실패를 결정적으로 주입한다.
- fake는 최초 생성과 기존 file 교체의 호출 형태, candidate byte, backup path와 원본 보존을 관찰한다.
- Win32 통합 test는 `std::filesystem::temp_directory_path()` 아래의 충돌 없는 전용 디렉터리를 만들고 test 종료 시 정리한다.
- 실제 target handle에서 delete sharing을 막아 `ReplaceFileW` 실패를 재현하며 repository 내부에 고정 artifact를 남기지 않는다.

## 5. 검증 결과

| 검증 | 결과 |
| --- | --- |
| VS2022 Debug build | 신규 save/recovery test를 포함해 통과 |
| 신규 save/recovery test subset | 9/9 통과 |
| `ctest --preset vs2022-debug --output-on-failure` | 전체 50/50 통과 |
| VS2026 Debug build | host 환경에서 신규 save/recovery test를 포함해 통과 |
| `ctest --preset vs2026-debug --output-on-failure` | 전체 50/50 통과 |
| clang-format dry run | 신규 C++ test source 통과 |
| line ending 및 source style | UTF-8 무 BOM, CRLF와 source style 검사 통과 |
| aggregate `gitman_format_check` | 변경하지 않은 기존 `utf8.cpp`, `win32_application.cpp`, `ui_theme.h`의 clang-format 위반으로 실패 |
| `git diff --check` 및 `git diff --cached --check` | 통과 |
| production source 변경 | 없음 |

build child process는 기존과 같이 중복 `PATH`/`Path`를 하나의 `Path`로 정규화했다. VS2026 build의 최초 sandbox 실행은 기존 FileTracker 제한으로 `E_ACCESSDENIED`가 발생했으며, 같은 build를 host 권한에서 실행해 통과했다.

## 6. 작성 중 검토 결과

새 test source의 multiline raw string initializer 2곳이 project source style의 독립된 닫는 중괄호 규칙에 맞지 않아 test source 안에서 형식을 바로잡았다. production 동작에는 영향이 없다.

집계 `gitman_format_check`도 실행했으나 이번 diff에 포함되지 않은 기존 `src/platform/win32/utf8.cpp`, `src/platform/win32/win32_application.cpp`, `src/presentation/ui_theme.h`에서 clang-format 19.1.5 위반을 보고했다. 신규 `json_project_store_tests.cpp`의 동일 formatter 직접 dry-run과 전체 source style 111개 파일 검사는 통과했다. 기존 파일은 test 체크포인트 범위 밖이므로 수정하지 않았고 별도 기준선 보정 사항으로 인수인계한다.

현재 알려진 production 결함과 `S2-D4-FIX` 후보는 없다.

## 7. 검수 완료

사용자가 2026-08-16에 진행을 지시해 `S2-D4-TEST`를 승인했다. production 결함 후보가 없어 `S2-D4-FIX`를 수정 없이 생략하고 `S2-D5-CODE`의 positional launch path production 구현으로 진행했다.
