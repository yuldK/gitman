# 단계 3 프로세스 실행 계층 최종 검증 기록

## 1. 검증 결론

단계 3의 production 구간, test 구간과 `S3-V1` 완료 조건을 모두 충족했다. 셸을 거치지 않는 인자 배열 실행, 출력 수집과 줄 단위 레코드, 활성 code page fallback, timeout과 취소, job object 트리 종료, 비밀 마스킹이 구현되고 검증됐다.

VS2022 Debug/Release와 VS2026 Debug의 전체 CTest가 각각 135/135 통과했다. VS2022 `/analyze`, aggregate format/style, Release install, 설치본 renderer smoke test와 PE 의존성 검사도 통과했다. 전체 suite 3회 반복과 동시 실행 stress 3회에서 실패나 순서 오류가 없었다.

현재 상태는 **단계 3 최종 사용자 검수 대기**다. 사용자 승인 전에는 단계 4를 시작하지 않는다.

## 3. 구현 범위

### 3.1 계약 계층

- 스트림, 완료 사유, 출력 레코드와 실행 결과를 `std::u8string` 기반 도메인 값으로 정의했다.
- 완료 사유는 `exited`, `start_failed`, `timed_out`, `cancelled`, `invalid_request`, `internal_error`다. 성공은 `exited`와 종료 코드 0, 오류 진단 없음을 모두 만족할 때만 참이다.
- 요청 검증은 filesystem을 조회하지 않고 절대 경로, NUL 문자, 중복 환경 override, timeout과 상한 값을 판정한다.
- 실행 API는 호출 스레드를 점유하는 동기 `run` 하나다. 카드별 lane과 결과 전달 경로는 단계 6~7의 scheduler와 message 설계가 정한다.
- 취소는 콜백 등록과 RAII 해제를 지원하는 source/token/registration으로 제공한다.

### 3.2 프로세스 시작

- `lpApplicationName`에 절대 경로를 넘겨 PATH 탐색과 확장자 추론을 사용하지 않는다.
- `CommandLineToArgvW` 규칙으로 인자를 인용하며 셸 metacharacter는 값의 일부로 남는다.
- stdin은 항상 `NUL`이므로 자식이 프롬프트를 읽으면 즉시 EOF가 된다.
- `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`로 표준 handle 세 개만 상속시킨다.
- 부모 환경 상속과 override 설정 및 삭제를 지원하며 이름 비교는 대소문자를 구분하지 않는다.
- 종료 코드는 상위 bit를 포함해 그대로 보존한다.

### 3.3 출력 수집

- pipe마다 전용 reader 스레드를 두어 한쪽 buffer가 차서 자식이 멈추는 상황을 막는다.
- 레코드는 줄 단위이며 `\r\n`, `\n`과 단독 `\r`(진행 표시)을 구분한다.
- 줄 끝 없이 상한에 도달하면 UTF-8 경계에서 끊고 `continued`를 세운다.
- 잘못된 byte는 U+FFFD로 대체하고, `active_code_page_fallback`에서는 유효한 UTF-8이 아닌 레코드만 활성 code page로 다시 해석한다.
- 실행 단위 단조 sequence를 mutex 아래에서 부여하므로 sink 구현은 스스로 동기화하지 않아도 된다.
- 스트림별 캡처 상한을 넘으면 이후 레코드를 버리고 warning 진단을 남기되 pipe는 계속 비운다.

### 3.4 timeout과 취소

- 이미 취소된 요청은 프로세스를 만들지 않는다.
- 자식을 `CREATE_SUSPENDED`로 시작해 kill-on-close job에 배정한 뒤 재개한다. 배정 전에 손자가 만들어지는 경쟁이 없다.
- 취소 token 콜백이 event를 신호하고 `WaitForMultipleObjects`가 프로세스와 함께 기다린다. polling이 없다.
- timeout과 취소는 트리를 종료하며, 종료로 pipe가 닫혀 reader 스레드가 EOF를 보고 끝난다. 두 스레드는 항상 join된다.
- 강제 종료한 실행은 종료 코드를 채우지 않고 그때까지 수집한 출력은 유지한다.
- job을 만들거나 배정하지 못하면 warning과 함께 단일 프로세스 종료로 물러선다.

### 3.5 비밀 마스킹

- URL userinfo, 자격 증명 option 6종, 헤더 형태 출력, `Basic` 자격 증명과 token 접두어 7종을 가린다.
- `std::regex` 대신 단일 통과 scanner를 사용하며 idempotent하다.
- 인코딩 확정 이후에 적용하므로 UTF-8과 code page fallback 경로 모두에서 sink 도달 전에 가려진다.
- 기록용 명령줄에만 적용하고 자식에게 넘기는 실제 인자는 바꾸지 않는다.

## 5. 동시 실행 stress

저장소 밖 임시 프로그램으로 4개 스레드가 각각 25회, 합계 100개 프로세스를 동시에 실행했다. 실행마다 출력 크기와 스트림 구성을 네 가지로 바꿔 경합을 넓게 흔들었다. 확인 후 프로그램은 삭제했다.

| 항목 | 1회 | 2회 | 3회 |
| --- | --- | --- | --- |
| 성공 / 실패 | 100 / 0 | 100 / 0 | 100 / 0 |
| 수집 레코드 | 112,525 | 112,525 | 112,525 |
| sequence 역전 | 0 | 0 | 0 |
| 소요 시간 | 1,525 ms | 742 ms | 791 ms |
| 프로세스 handle | 71 → 77 | 65 → 71 | 65 → 71 |

레코드 수가 세 번 모두 같아 수집이 결정적임을 확인했다. handle 증가폭은 매번 고정된 6개이며 반복해도 누적되지 않는다. 스레드 pool과 CRT 내부 구조가 최초 사용 시 만드는 handle이며 실행별 누수가 아니다.

## 6. 단일 실행 파일 확인

Release install 결과는 `bin/gitman.exe` 한 파일이다.

| 항목 | 값 |
| --- | --- |
| 크기 | 6,255,616 byte |
| SHA-256 | `16F3C44406A7992439C34048A47FCEDD2B9937010FD899B35D2FC2B77167662D` |

`dumpbin /dependents` 결과는 `ole32.dll`, `SHELL32.dll`, `d3d12.dll`, `dxgi.dll`, `D3DCOMPILER_47.dll`, `dwmapi.dll`, `GDI32.dll`, `USER32.dll`, `KERNEL32.dll`뿐이다. VC runtime, Skia, ICU, Catch2와 프로젝트 DLL은 없다.

test 전용 `gitman_process_test_child` target은 install rule이 없으므로 배포에 포함되지 않는다.

크기가 단계 2와 같은 이유는 `gitman_process` library를 아직 실행 파일이 링크하지 않기 때문이다. 프로세스 실행 계층은 단계 4에서 Git/SVN provider가 사용할 때 실행 파일에 들어간다. 현재는 library와 test로만 검증된 상태다.

## 7. 계획 대비 변경

| 변경 | 사유 |
| --- | --- |
| 출력 pipe와 줄 단위 레코드가 `S3-D3`에서 `S3-D2`로 이동 | 사용자 검수 지시. runner가 더 이른 시점에 실용성을 갖추게 했다. |
| `process_completion::internal_error` 추가 | wait, reader 스레드 생성, 종료 코드 확인 실패를 `exited`로 보고하지 않기 위해서다. |
| runner와 transcoder 파일의 target을 `gitman_process`로 배치 | `gitman_win32_platform`에 넣으면 static library 순환 참조가 생긴다. 파일 위치는 계획대로 `platform/win32`에 유지했다. |
| 레코드 크기 상한의 최소값 4 byte 도입 | 강제 분할이 UTF-8 sequence 하나를 쪼개지 않게 하기 위해서다. |
| 도우미를 argv 기반 실행 파일로 확정 | `cmd.exe`는 `CommandLineToArgvW` 규칙이 아닌 자체 따옴표 처리를 해 인용 검증이 잘못 실패한다. |

체크포인트 수 17개와 `CODE` / `TEST` / `FIX` 분할은 계획대로 유지했다.

## 8. 보류 및 후속 단계 경계

- Git/SVN 실행 파일 탐색, `--version` 확인과 명령 인자 조립, 출력 파싱은 단계 4 범위다.
- 기본 timeout, 기본 캡처 상한과 `LC_ALL` 같은 로캘 강제 여부는 명령별로 정할 사항이라 단계 4에서 확정한다.
- 카드별 `operation_lane`, 저장소별 직렬화와 전체 동시 실행 상한은 단계 6~7의 `task_scheduler` 범위다.
- 카드별 로그 ring buffer, 진행 표시 접힘 UX와 하단 터미널은 단계 7 범위다.
- ADR-004의 범용 message 구조는 단계 6 전 별도 설계 승인 없이 구현하지 않는다. 단계 3의 reader 스레드는 실행 하나에 종속된 내부 구현이며 이 차단 조건에 해당하지 않는다.
- job object를 사용할 수 없는 환경에서는 손자 프로세스 정리가 보장되지 않는다. warning 진단으로 알린다.
- 마스킹은 값의 끝을 공백과 줄 끝으로 판정하므로 자격 증명에 붙은 구두점이 함께 가려질 수 있다.
- 단계 1의 caption 수동 검수 체크리스트 미확인 항목은 계속 보존한다.

## 10. 최종 검수 게이트

단계 3 자동 완료 조건은 충족했다. 사용자가 본 기록과 변경 내용을 최종 승인하기 전에는 단계 4 Git 및 SVN provider를 시작하지 않는다.
