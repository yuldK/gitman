# 단계 3 `S3-D1-CODE` 검증 기록 - 2026-08-16

## 1. 결과

프로세스 실행 계층의 계약 계층만 구현했다. 프로세스 실행 값 model, 요청 검증, runner 및 output sink 추상 계약, 취소 primitive와 새 `gitman_process` CMake target을 추가했다. 실제 `CreateProcessW` 실행, 출력 파이프라인과 마스킹은 각각 `S3-D2-CODE`, `S3-D3-CODE`, `S3-D5-CODE` 범위이므로 포함하지 않았다.

VS2022와 VS2026 Debug build가 통과했고 기존 전체 CTest가 양 toolchain에서 각각 54/54 통과했다. 이번 체크포인트에서는 새 test source를 작성하지 않았다.

기존 aggregate `gitman_format_check`에서 이번 변경과 무관한 3개 파일의 위반을 발견했다. 5장에 사실대로 기록했다.

## 2. 구현 범위

### 2.1 도메인 값 model

`src/domain/process_execution.h/.cpp`에 다음을 추가했다.

| 값 | 내용 |
| --- | --- |
| `process_stream` | `standard_output`, `standard_error` |
| `process_completion` | `exited`, `start_failed`, `timed_out`, `cancelled`, `invalid_request` |
| `process_output_record` | 실행 단위 `sequence`, 스트림, UTF-8 및 마스킹 완료 `text`, `progress`, `continued`, `replaced_invalid_bytes`, `transcoded_from_active_code_page` |
| `process_result` | 완료 사유, optional 종료 코드, 시작 및 종료 시각, 실행 시간, 레코드 수, 캡처 byte, 절단 표시, Win32 error code, 마스킹된 명령줄, 진단 |

`process_result::succeeded()`는 `exited`와 종료 코드 0, 오류 진단 없음을 모두 만족할 때만 참이다. timeout과 취소는 자식이 남긴 종료 코드를 신뢰하지 않으므로 `exit_code`를 채우지 않는다.

`domain/diagnostic.h`에는 `invalid_process_request`, `process_start_failed`, `process_pipe_failed`, `process_timed_out`, `process_cancelled`, `process_output_truncated` code를 추가하고 이름 매핑도 갱신했다.

### 2.2 요청 값과 검증

`src/application/process_request.h/.cpp`는 실행 파일, 인자 배열, 작업 디렉터리, 환경 override, optional timeout, 스트림별 캡처 상한, 레코드 크기 상한과 `process_text_encoding`을 담는다. `validate_process_request`는 filesystem을 조회하지 않고 값만으로 다음을 판정한다.

| 검증 | 이유 |
| --- | --- |
| 빈 실행 파일 및 빈 작업 디렉터리 | 필수 값이다. |
| 절대 경로가 아닌 실행 파일 및 작업 디렉터리 | PATH 탐색과 확장자 추론을 하지 않으므로 상대 경로는 호출자의 현재 디렉터리에 따라 다른 프로그램을 실행할 수 있다. |
| 실행 파일, 작업 디렉터리, 인자의 NUL 문자 | Win32 command line과 경로는 NUL로 끝나므로 값 안의 NUL은 잘림을 유발한다. |
| 빈 환경 변수 이름, 이름의 `=`와 NUL, 값의 NUL | 환경 block 형식을 깨뜨린다. |
| ASCII 대소문자 무시 중복 환경 override | Windows 환경 변수 이름은 대소문자를 구분하지 않아 적용 순서에 따라 결과가 달라진다. |
| 0 이하 timeout | 즉시 종료를 뜻하는 값을 실수로 넘기는 것을 막는다. |
| 0인 캡처 상한 | 출력을 전혀 수집하지 않는 요청은 명시적 오류로 본다. |
| 4 byte 미만 레코드 상한 | 강제 분할이 UTF-8 sequence 하나를 쪼개지 않도록 최소값을 둔다. |

`is_absolute_windows_path`는 Win32 API 없이 어휘적으로만 판정한다. `C:\`와 `C:/`, `\\server\share`, `\\?\C:\`를 절대 경로로 보고 `C:relative`, `\rooted`, 빈 값은 거부한다.

`default_process_record_byte_limit`은 8 KiB, `process_read_block_byte_size`는 64 KiB로 두었다. 계획 11장에 따라 기본 timeout과 기본 캡처 상한은 강제하지 않고 호출자가 명시하게 남겼다.

### 2.3 runner와 sink 계약

`src/application/process_runner.h`는 구현 없는 추상 계약만 정의한다.

- `process_output_sink::on_record`는 runner가 내부 mutex로 직렬화해 호출하므로 sink 구현은 스스로 동기화하지 않아도 된다. 대신 sink에서 오래 기다리면 자식이 backpressure를 받는다는 계약을 주석으로 남겼다.
- `process_runner::run(request, sink, token)`은 호출 스레드를 점유하는 동기 API 하나다. `sink`는 null일 수 있고 그때도 출력은 계속 비운다.
- 하나의 runner instance는 여러 스레드에서 동시 호출이 가능해야 한다는 요구를 계약에 명시했다.

카드별 lane, 동시 실행 상한과 결과 전달 경로는 단계 6~7의 scheduler 및 message 설계 범위로 남겼다. 따라서 이번 계약에는 queue, dispatcher, envelope가 없고 ADR-004의 구현 차단 조건을 건드리지 않는다.

### 2.4 취소 primitive

`src/application/process_cancellation.h/.cpp`는 `process_cancellation_source`, 복사 가능한 `process_cancellation_token`과 RAII `process_cancellation_registration`을 제공한다.

- 기본 생성한 token은 절대 취소되지 않으므로 취소가 필요 없는 호출자는 빈 token을 그대로 넘길 수 있다.
- `register_callback`은 이미 취소된 token이면 콜백을 즉시 같은 스레드에서 실행하고 등록하지 않는다.
- 취소 요청은 mutex를 잡은 상태에서 콜백을 실행한다. 따라서 registration 소멸이 콜백 실행과 겹쳐도 콜백이 끝난 뒤에만 해제되어 dangling 참조가 생기지 않는다. 반대로 콜백이 자신의 registration을 소멸시키면 안 되며 이 제약을 헤더 주석에 남겼다.
- `cancelled()`는 mutex 없이 atomic만 읽으므로 대기 loop에서 저렴하다.
- 상태 구현체는 `gitman::detail`에 두고 헤더에는 전방 선언만 노출했다. 따라서 상위 계층은 `<mutex>`와 구현 세부를 보지 않는다.

Win32 runner는 `S3-D2-CODE`에서 이 token에 event를 신호하는 콜백을 등록해 polling 없이 대기한다.

### 2.5 build 구성

- `gitman_domain`에 `domain/process_execution.*`를 추가했다.
- 새 static library `gitman_process`를 만들고 `gitman_domain`을 PUBLIC으로 링크했다. Win32 구현이 들어오는 `S3-D2-CODE`에서 `gitman_win32_platform`을 PRIVATE으로 추가한다.
- `tests/CMakeLists.txt`는 이번 구간에서 변경하지 않았다. `gitman_process` 링크는 test 구간인 `S3-D1-TEST`에서 추가한다.

## 5. 발견한 기존 문제

aggregate `gitman_format_check`가 이번 변경과 무관한 3개 파일에서 실패한다.

- `src/platform/win32/utf8.cpp`
- `src/platform/win32/win32_application.cpp`
- `src/presentation/ui_theme.h`

`docs/verification/2026-08-16-stage-2.md` 6장은 `S2-V1`에서 이 위반을 해소하고 aggregate 검사가 최종 통과했다고 기록했다. 그러나 커밋 `5c1a19a`에는 `win32_application.cpp`만 포함됐고 나머지 두 파일의 정렬은 커밋되지 않았다. 커밋된 `win32_application.cpp`도 현재 검사를 통과하지 않는다. 따라서 해당 기록은 현재 저장소 상태와 일치하지 않는다.

원인은 도구 오류가 아니라 규칙 충돌이다. `docs/code_style.md` 2장은 긴 표현식을 수동으로 줄바꿈하고 닫는 기호를 별도 줄에 두라고 요구하지만, `ColumnLimit`이 200인 clang-format은 같은 표현식을 한 줄로 다시 합친다. 세 파일은 모두 이 수동 줄바꿈 형태를 사용한다.

선택 가능한 처리 방향은 다음과 같으며 `S3-D1-CODE` 범위 밖이라 이번 구간에서는 변경하지 않았다.

| 방향 | 결과 |
| --- | --- |
| clang-format 결과를 그대로 수용 | 세 파일의 수동 줄바꿈이 한 줄로 합쳐진다. 자동 검사는 통과하지만 문서 규칙과 어긋난다. |
| `// clang-format off` / `on`으로 감싸기 | 문서 규칙과 자동 검사를 모두 만족한다. 예외 구간이 코드에 보인다. |
| 알려진 기준선 이탈로 유지 | 코드 변경이 없지만 aggregate 검사가 계속 실패한다. |

이번 체크포인트에서 추가한 source는 aggregate 검사와 문서 규칙을 모두 만족한다.

## 6. 구현 중 검토 결과

- 프로세스 진단에는 `diagnostic_source`를 사용하지 않기로 확인했다. `diagnostic_source`는 문서 경로와 JSON pointer 중심이라 실행 파일 경로를 담기에 의미가 맞지 않는다. 실행 문맥은 `process_result::masked_command_line`과 메시지가 제공한다. 계획 4.6의 확인 항목을 이렇게 정리했다.
- 활성 code page fallback transcoder 인터페이스는 출력 파이프라인과 함께 정의하는 편이 응집도가 높아 `S3-D3-CODE`로 미뤘다. 요청 값의 `process_text_encoding`은 이번 구간에 포함했다.
- 현재 알려진 계약 production 결함은 없다. 새 동작의 전용 test는 체크포인트 분리 규칙에 따라 아직 작성하지 않았다.
