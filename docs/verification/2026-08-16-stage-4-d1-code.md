# 단계 4 `S4-D1-CODE` 검증 기록 - 2026-08-16

## 1. 결과

단계 4의 계약 계층만 구현했다. 도메인 확장, 문서 `settings` 스키마와 저장, provider 및 registry와 probe 계약, 도구 탐색과 버전 비교, 비대화형 실행 정책, 로캘 독립 오류 분류기, 새 `gitman_vcs` CMake target을 추가했다.

Git/SVN 명령 조립과 출력 파싱, update와 switch는 각각 `S4-D2-CODE` 이후 범위이므로 포함하지 않았다.

VS2022 Debug/Release와 VS2026 Debug build가 통과했고 기존 전체 CTest가 양 toolchain에서 각각 139/139 통과했다. VS2022 `/analyze`가 경고 없이 통과했고 aggregate `gitman_format_check`와 `gitman_source_style`도 통과했다. 이번 체크포인트에서는 새 test source를 작성하지 않았다.

저장소 밖 임시 프로그램으로 69개 항목을 수동 확인하고 삭제했다. 5장에 결과를 기록한다.

## 2. 구현 범위

### 2.1 도메인 확장

| 파일 | 내용 |
| --- | --- |
| `domain/vcs_tool.h/.cpp` (신규) | `vcs_tool_availability`, `vcs_tool_version`, `vcs_tool_info`, `vcs_tool_set`, 최소 버전 상수 |
| `domain/vcs_operation.h/.cpp` (신규) | `switch_candidate`, `switch_rejection`, `switch_validation_result`, `update_block_reason`, `update_options`와 한국어 메시지 |
| `domain/path_syntax.h/.cpp` (신규) | `is_absolute_windows_path`를 단계 3의 `application/process_request`에서 도메인으로 옮김 |
| `domain/project.h/.cpp` | `workspace_settings`와 `workspace_document::settings` |
| `domain/repository_snapshot.h/.cpp` | `repository_availability`, `remote_sync_state::authentication_required`, 작업 트리 확장, `submodule_status`, SVN 필드 |
| `domain/diagnostic.h/.cpp` | VCS 관련 diagnostic code 11개와 이름 매핑 |

`is_absolute_windows_path`를 도메인으로 옮긴 이유는 문서 `settings`의 실행 파일 경로 검증과 프로세스 요청 검증이 같은 규칙을 써야 하기 때문이다. `gitman_workspace`는 `gitman_process`를 링크하지 않으므로 그대로 두면 규칙이 두 벌이 된다. `application/process_request.h`가 새 도메인 헤더를 include하므로 기존 호출자와 test는 변경 없이 컴파일된다.

`working_tree_summary::is_safe_for_change()`는 `clean`이 아니거나 진행 중 작업 또는 `index.lock`이 있으면 거짓이다. `unknown` 상태도 안전하다고 보지 않는다. 모르는 상태에서 변경 명령을 실행하는 편이 더 위험하다.

`has_switched_subtree`와 `has_mixed_revision`은 `std::optional<bool>`이다. `svnversion`이 없는 환경에서는 판정할 수 없으므로 거짓과 미상을 구분한다.

### 2.2 모든 VCS가 없는 환경

사용자 지시에 따라 Git과 SVN이 **둘 다 없는 환경**을 1급 상태로 다룬다.

- `repository_availability::tool_unavailable`로 카드가 목록에 남은 채 동작만 비활성화되는 상태를 표현한다.
- `vcs_tool_set::none_available()`과 `vcs_tool_registry::none_available()`로 전체 비활성화를 한 번에 판단한다.
- 도구 부재 진단의 severity는 **warning**이다. 앱을 멈추는 오류가 아니며 다른 VCS와 프로젝트 목록은 계속 사용할 수 있다.
- `repository_provider::available()`을 계약에 넣어 호출자가 조회와 변경을 시도하기 전에 걸러낼 수 있게 했다.

### 2.3 문서 `settings`

`.version-list`에 optional `settings` object를 추가했다. 스키마 버전은 1을 유지한다.

```json
{
    "schema_version": 1,
    "settings": {
        "git_executable": "C:/Program Files/Git/cmd/git.exe",
        "svn_executable": ""
    },
    "projects": []
}
```

| 규칙 | 구현 |
| --- | --- |
| 없으면 기본값 | `settings`가 없거나 `null`이면 진단 없이 전부 자동 탐색이다. 기존 fixture 6종이 그대로 통과한다. |
| 값 형식 | 빈 문자열은 "지정하지 않음"이다. 값이 있으면 `is_absolute_windows_path`로 절대 경로를 요구하고 위반은 `vcs_tool_path_invalid` 오류다. |
| 알 수 없는 키 | `/settings/<key>` pointer와 함께 warning으로 보고하고 저장 시 보존한다. |
| 저장 | 기존 `settings` object를 template으로 삼아 알 수 없는 키를 유지한다. 문서에 없었고 값도 기본값이면 필드를 만들지 않아 기존 문서 형태를 바꾸지 않는다. |

### 2.4 도구 탐색과 버전 비교

`infrastructure/vcs_tool_discovery.*`와 `infrastructure/vcs_version.*`을 추가했다.

- 탐색 순서는 `settings` 지정 경로 → `PATH` → 알려진 기본 설치 위치다.
- `split_search_path`는 따옴표를 벗기고 빈 항목과 상대 경로 항목을 버리며 ASCII 대소문자를 무시하고 중복을 제거한다. 상대 경로를 버리는 이유는 호출자의 현재 디렉터리에 따라 다른 실행 파일이 잡힐 수 있기 때문이다.
- `vcs_tool_candidates`는 filesystem을 조회하지 않는 순수 함수다. 탐색 규칙 자체를 프로세스 없이 test할 수 있다.
- **지정 경로가 있으면 다른 후보를 만들지 않는다.** 지정 경로가 상대 경로거나, 존재하지 않거나, `--version`이 실패하면 `path_invalid`로 보고하고 자동 탐색으로 물러서지 않는다. 사용자가 지정한 값이 조용히 무시되는 편이 더 위험하다.
- 버전 파싱은 접두어를 고정하지 않고 첫 줄에서 `숫자.숫자` 토큰을 찾는다. `git version 2.52.0.windows.1`과 `svn, version 1.14.5 (r1922182)`를 모두 처리하고 네 번째 이후 구성 요소는 비교에 쓰지 않는다. patch가 없는 `2.43` 표기도 허용한다.
- `svnversion.exe`는 `svn.exe`와 같은 디렉터리에서 찾아 `auxiliary_executable`에 담는다. 없으면 조회를 막지 않고 mixed revision 및 switched 판정만 포기한다.
- `--version` 실행의 작업 디렉터리는 실행 파일이 있는 디렉터리다. 단계 3 계약이 절대 경로 작업 디렉터리를 요구하는데 이 시점에는 대상 저장소가 정해지지 않았기 때문이다.

### 2.5 비대화형 실행 정책

`infrastructure/vcs_execution_policy.*`에 명령 부류별 제한과 공통 환경 및 인자를 모았다.

| 명령 부류 | timeout | 스트림당 캡처 상한 |
| --- | --- | --- |
| `tool_probe` | 5초 | 64 KiB |
| `local_query` | 30초 | 8 MiB |
| `remote_query` | 120초 | 8 MiB |
| `update` | 600초 | 32 MiB |
| `switch_target` | 300초 | 8 MiB |

Git 환경 override는 `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=Never`, `GIT_SSH_COMMAND=ssh -oBatchMode=yes`, `GIT_OPTIONAL_LOCKS=0`과 `GIT_ASKPASS`, `SSH_ASKPASS`, `DISPLAY` 삭제다. 공통 인자는 `-c core.quotepath=false`, `-c gc.auto=0`, `-c color.ui=false`, `--no-pager`다. SVN은 `--non-interactive`만 붙인다.

**로캘은 강제하지 않는다.** 사용자 결정에 따라 시스템 언어 메시지를 그대로 보여 준다. 따라서 인코딩 모드는 Git 포함 모든 명령에서 `active_code_page_fallback`이다. 유효한 UTF-8 레코드는 변환하지 않으므로 `core.quotepath=false`로 얻는 UTF-8 경로 출력에는 영향이 없다.

### 2.6 로캘 독립 오류 분류

`infrastructure/vcs_error_classifier.*`는 번역되는 메시지 본문으로 분류하지 않는다.

| 신호 | 근거 |
| --- | --- |
| SVN `E<숫자>` 코드 | 번역된 메시지에도 코드가 그대로 붙는다 |
| libcurl 문자열 | libcurl에는 번역 catalog가 없다 |
| OpenSSH 문자열 | 같은 이유로 번역되지 않는다 |
| HTTP 상태 번호 | 감싸는 문장이 번역되어도 숫자 인자는 남는다 |

HTTP 상태는 오탐을 줄이려고 두 조건을 함께 요구한다. 앞뒤가 숫자가 아닌 독립 토큰이어야 하고, 같은 텍스트에 `http`가 있어야 한다. 그래서 `branch 404 checked out` 같은 출력은 분류에 걸리지 않는다.

SVN은 인증 → 저장소 → 네트워크 순으로 코드를 확인한다. `E170013`(연결 실패)이 더 구체적인 `E215004`(자격 증명 없음)와 함께 나오는 경우가 많아 연결 코드를 뒤에 둔다.

어느 신호에도 맞지 않으면 추측하지 않고 `command_failed`로 보고한다. 잘못된 `offline` 판정보다 안전하다. 번역 대상인 `Authentication failed`, `not a git repository` 등은 위 신호가 모두 없을 때만 보는 보조 신호로 남겼다.

### 2.7 계약과 build 구성

- `application/repository_provider.h`는 `query_local`, `query_remote`, `query_switch_candidates`, `update`, `switch_to`와 `available()`을 정의한다. 모두 동기 API이며 예외를 던지지 않는다.
- `repository_change_result::executed`가 거짓이면 어떤 `process_request`도 만들지 않았다는 뜻이다. REQ-007의 수용 기준을 계약 수준에서 관측 가능하게 만든 값이다.
- `application/vcs_file_probe.h`는 git dir 표식 파일 확인 계약이다. Git에 진행 중 작업을 알려 주는 기계 판독 명령이 없어 filesystem 접근이 필요하고, 계층 규칙을 지키려고 계약으로 분리했다.
- `application/vcs_tool_registry.*`는 조사 결과를 담는 값 container다. 탐색 로직은 infrastructure에 있어 application이 infrastructure를 참조하지 않는다.
- `infrastructure/vcs_command_runner.*`는 요청을 실행하고 stdout과 stderr를 분리해 모으며 호출자 sink에도 그대로 전달한다. 카드 로그는 단계 7에서 이 자리에 들어간다.
- 새 static library `gitman_vcs`가 `gitman_domain`과 `gitman_process`를 PUBLIC, `gitman_win32_platform`을 PRIVATE으로 링크한다.

## 3. 계획과 다른 점

`platform/win32/win32_vcs_file_probe.*`를 계획의 `gitman_win32_platform` 대신 `gitman_vcs` target에 넣었다. 이 파일이 `vcs_tool_environment`를 만들려면 infrastructure 헤더가 필요한데, platform target이 상위 계층 헤더를 참조하면 방향이 뒤집힌다. 단계 3에서 `win32_process_runner`를 `gitman_process`에 넣은 것과 같은 이유이며 파일 위치는 계획대로 유지했다.

`vcs_command_runner`는 계획 5장에 있던 파일이지만 `--version` 실행에 필요해 `S4-D1-CODE`에서 함께 구현했다.

## 5. 수동 확인 결과

저장소 밖 임시 프로그램으로 69개 항목을 확인하고 삭제했다. 모두 통과했다.

| 구간 | 확인 내용 |
| --- | --- |
| 버전 파싱 | Git과 SVN 정상 형식, `2.43` 축약, 잘못된 형식, 빈 값, 최소 버전 경계, 여러 줄 출력의 첫 줄 사용 |
| 탐색 | `PATH` 분해에서 빈 항목·상대 경로 제거와 대소문자 무시 중복 제거, 따옴표 제거, 실행 파일 디렉터리 계산, 지정 경로의 자동 탐색 차단 |
| 오류 분류 | ssh 및 HTTP 401/403 인증, libcurl 연결 실패, `Repository not found`, SVN `E215004`/`E170013`/`E155007`, 미분류 실패, `404` 오탐 방지 |
| 실행 정책 | 생성한 요청이 단계 3 검증을 통과, 공통 인자 순서, `gc.auto=0`, fallback 인코딩, timeout, 환경 override, 로캘 미강제 |
| `settings` | 정상 parse, 빈 값, 알 수 없는 키 warning과 pointer, 상대 경로 거부, `settings` 부재 시 진단 없음 |
| 호스트 조사 | Git 2.52.0 발견, SVN 미설치 `not_found`, warning severity, registry 판정 |
| 전체 부재 | 빈 `PATH`에서 두 도구 모두 `not_found`, `none_available()` 참, 진단이 모두 warning |
| 지정 경로 | 없는 경로와 상대 경로는 `path_invalid`, 유효한 경로는 manual 표시로 사용 |

한국어 메시지 분류 항목을 일부러 넣었다. `치명적: ... Could not resolve host: x`처럼 Git이 문장을 번역해도 libcurl 부분이 남아 `offline`으로 분류되는 것을 확인했다.

임시 프로그램의 기대값 오류 2건을 발견해 고쳤다. `PATH`에서 `C:\A\`가 `C:\a`의 대소문자 무시 중복으로 제거되는데 처음에 이를 세지 않았다. production 결함이 아니라 의도한 동작이며 `S4-D1-TEST`에서 test로 고정한다.
