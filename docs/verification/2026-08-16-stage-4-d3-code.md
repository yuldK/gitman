# 단계 4 `S4-D3-CODE` 검증 기록 - 2026-08-16

## 1. 결과

Git의 remote-first 최신 상태 판정을 구현했다. remote 열거, 비교 대상 선택, `fetch --prune`, ahead/behind 계산과 offline·인증 필요·오류 구분이다. `query_remote`가 이제 실제로 동작한다.

SVN(`S4-D4`), update(`S4-D5`), switch(`S4-D6`)는 포함하지 않았다. 두 동작과 switch 후보 조회는 여전히 어떤 process request도 만들지 않는다.

VS2022 Debug/Release와 VS2026 Debug build 및 전체 CTest가 각각 246/246 통과했다. VS2022 `/analyze`가 경고 없이 통과했고 aggregate `gitman_format_check`, `gitman_source_style`, `gitman_assets_checksum`, `git diff --check`도 통과했다.

저장소 밖 임시 프로그램으로 124개 항목을 수동 확인하고 삭제했다. 그중 11개는 실제 `git.exe`와 실제 임시 저장소 7종을 사용한 확인이다. 5장에 결과를 기록한다.

### 2.2 remote-first 순서

ADR-003과 계획 4.5의 순서를 구현했다.

| 순서 | 동작 | 실패 시 |
| --- | --- | --- |
| 1 | 도구·로컬 상태·경로 확인 | 명령을 만들지 않고 사유만 보고 |
| 2 | detached HEAD면 즉시 `remote_target_missing` | 네트워크를 쓰지 않는다 |
| 3 | `git remote`로 remote 열거 | remote가 없으면 `local_only`, fetch하지 않음 |
| 4 | 비교 대상 선택 | 자동으로 좁혀지지 않으면 `remote_target_missing`, fetch하지 않음 |
| 5 | `fetch --prune -- <remote>` | 분류기로 `offline` / `authentication_required` / `error` 구분 |
| 6 | `rev-parse --verify --quiet <tracking ref>` | 없으면 `remote_target_missing`. local 비교로 물러서지 않음 |
| 7 | `rev-list --left-right --count HEAD...<tracking ref>` | 해석 못 하면 `error` |
| 8 | `comparison=remote`, `comparison_target`, ahead/behind, `remote_checked_at` | |

비교 대상 선택은 `select_git_remote_target` 순수 함수다. 프로세스와 filesystem을 쓰지 않아 규칙만 따로 검증할 수 있다.

| 규칙 | 결과 |
| --- | --- |
| upstream이 remote를 가리킴 | 그대로 사용 |
| `preferred_remote`가 설정에 있음 | 그 remote |
| `origin`이 있음 | `origin` |
| remote가 하나뿐 | 그 remote |
| 그 밖 | `ambiguous_remote`. **자동으로 고르지 않는다** |

upstream에서 remote 이름을 뗄 때는 설정된 remote 중 **가장 긴 접두사**를 고른다. branch 이름에도 `/`가 들어갈 수 있어 첫 `/`로 자르면 `origin/feature/a/b`를 잘못 나눈다.

`branch.<name>.remote = .`처럼 upstream이 local branch를 가리키는 경우에는 원격 비교에 쓸 수 없으므로 나머지 규칙으로 넘어간다.

지정한 `preferred_remote`가 저장소에 없으면 `preferred_remote_missing` 표시를 남기고 다음 규칙(`origin` → 유일한 remote)으로 진행하되 **warning 진단을 함께 보고한다**. 지정한 값이 조용히 무시되면 사용자는 다른 remote와 비교되고 있다는 사실을 알 수 없다.

### 2.3 실패해도 지우지 않는 값

`query_remote`는 로컬 상태를 다시 만들지 않고 받은 snapshot을 복사해 원격 값만 덮어쓴다. 따라서 fetch가 실패해도 작업 트리 상태, 마지막 성공 원격 확인 시각(`remote_checked_at`), 직전 로컬 비교(`comparison_source::local`과 ahead/behind)가 그대로 남는다. 사용자는 "지금은 연결이 안 되지만 마지막으로 알기로는 2개 앞서 있었다"를 볼 수 있다.

반대로 비교 대상 자체가 없다고 판정한 경우(`local_only`, `remote_target_missing`)에는 이전 비교 값을 지운다. 유효하지 않은 비교를 남겨 두면 카드가 잘못된 수를 계속 보여 준다.

`remote_checked_at`은 **fetch가 성공한 시각**이다. 그 뒤 비교 대상이 없어도 원격에 닿은 것은 사실이므로 시각은 남긴다.

### 2.4 명령 형태와 확인한 Git 동작

호스트의 Git 2.52.0으로 실측해 다음을 확정했다.

| 명령 | 확정 내용 |
| --- | --- |
| `fetch --prune -- <remote>` | `--`가 동작한다. remote 이름은 저장소 설정에서 오므로 `-`로 시작하는 값이 인자로 해석되지 않게 끊는다. |
| `rev-parse --verify --quiet <ref>` | **`--`를 쓰면 안 된다.** `rev-parse`의 `--`는 뒤의 값을 경로로 만들어 항상 실패한다. 대신 호출자가 `refs/`로 시작하는 완전한 ref만 넘긴다. |
| `rev-parse --verify --quiet` | 없는 ref는 출력 없이 종료 코드 1이다. 메시지 언어와 무관하게 판정할 수 있다. |
| `rev-list --left-right --count HEAD...<ref>` | `<ahead>\t<behind>` 한 줄이다. `HEAD`를 쓰면 branch 이름을 인자로 넘기지 않아 이름에 특수 문자가 있어도 안전하다. |

fetch는 `remote_query` 부류라 timeout 120초, 나머지는 `local_query` 부류라 30초다.

### 2.5 커밋이 없는 저장소

커밋이 하나도 없으면 `HEAD`가 없어 대칭 차이를 계산할 수 없다. 이때는 fetch와 ref 확인까지만 하고 `comparison=remote`, `comparison_target`을 채운 뒤 `sync_state`를 `unknown`으로 두고 정보 진단을 남긴다. 추측한 값을 넣지 않는다.

## 3. 계획과 다른 점

1. 계획 4.5는 remote branch 존재 확인(4번)을 fetch(5번)보다 앞에 뒀지만, 구현은 **fetch 뒤에 확인**한다. 한 번도 fetch하지 않은 저장소에는 tracking ref가 없어서, fetch 전에 확인하면 원격에 있는 branch를 없다고 오판한다. 판정 결과(`remote_target_missing`, local로 물러서지 않음)는 계획과 같다.
2. `fetch --prune`에 `--`를 붙였다. 계획에 없는 인자지만 remote 이름이 옵션으로 해석되는 것을 막는 안전장치이며 실측으로 동작을 확인했다.
3. `preferred_remote`가 없을 때 조회를 중단하지 않고 다음 규칙으로 진행하며 warning을 남긴다. 계획은 이 경우를 다루지 않았다.
4. 비교 대상 선택을 `select_git_remote_target` 자유 함수로 `git_repository_provider.h`에 공개했다. `S4-D2-CODE`의 `detect_git_in_progress_markers`와 같은 방식이며 계획 5장의 파일 목록을 늘리지 않는다.


libcurl이 만든 영어 문장이 그대로 남아 로캘과 무관하게 `offline`으로 분류된다. 한국어 Git 메시지에 `Permission denied (publickey)`가 섞인 경우가 `authentication_required`로 분류되는 것도 fake runner 확인 항목에 넣었다.
