# 단계 2 도메인과 설정 저장소 최종 검증 기록

## 1. 검증 결론

단계 2의 production 구현, test 체크포인트와 `S2-V1` 자동 완료 조건을 모두 충족했다. `.verison-list` 작업공간 문서의 schema v1 load/save, 부분 성공, 경로 정규화와 중복 판정, exact-byte 동시 수정 감지, 원자적 저장, backup 탐지와 명시적 복구 및 positional launch path 계약이 구현됐다.

VS2022 Debug/Release와 VS2026 Debug의 전체 CTest가 각각 54/54 통과했다. VS2022 `/analyze`, aggregate format/style, Release install, 설치본 renderer smoke test와 PE 의존성 검사도 통과했다. 현재 상태는 **단계 2 완료**다. 2026-08-16 사용자가 단계 3 진행을 지시하며 최종 승인했다.

## 3. 구현 범위

### 3.1 도메인과 진단

- `std::u8string` 기반 project ID, 원문 및 정규화 path, VCS hint와 repository snapshot을 제공한다.
- 작업 종류와 상태, opaque operation ID 및 안정적인 diagnostic code, severity와 source location을 제공한다.
- public domain과 application 계약은 Win32, Skia와 nlohmann/json type을 노출하지 않는다.

### 3.2 schema와 부분 성공

- schema version 1의 최소, 전체 및 빈 문서를 읽는다.
- 문서 수준 오류와 항목 수준 오류를 구분하며 잘못된 project가 섞여 있어도 유효 project를 반환한다.
- optional 기본값, 중복 ID, 지원하지 않는 이전 및 미래 version을 검증한다.
- 알 수 없는 top-level 및 project field를 warning으로 보고하고 JSON shadow에 보존한다.

### 3.3 경로

- 상대 path를 작업공간 문서 디렉터리 기준으로 해석한다.
- drive, UNC, extended path, slash, `.` 및 `..`, trailing separator와 대소문자를 Windows 비교 규칙으로 정규화한다.
- 사용자가 입력한 UTF-8 path 원문은 저장용 값으로 별도 보존한다.
- directory, missing, not-directory 및 invalid 상태와 lexical duplicate를 판정한다.

### 3.4 저장과 복구

- load 당시 원본 byte에서 opaque revision token을 만들고 save 직전에 exact byte를 다시 비교한다.
- 외부 변경이 있으면 `concurrent_modification`으로 실패하고 원본을 교체하지 않는다.
- 저장 후보 전체를 serialize 및 재검증한 뒤 같은 디렉터리의 임시 파일에 UTF-8 무 BOM, 공백 4칸과 CRLF로 쓴다.
- `FlushFileBuffers` 후 기존 파일은 `ReplaceFileW`와 `.bak`으로 교체하고 최초 생성은 write-through 이동을 사용한다.
- write, flush 및 replace 실패를 구조화 diagnostic으로 반환하고 기존 byte와 임시 파일 정리 계약을 보존한다.
- 손상 primary를 backup으로 자동 대체하지 않는다. 유효한 backup만 후보로 알리고 명시적 backup load와 승인된 save로 복구한다.

### 3.5 실행 진입 계약

- 작업공간 문서 경로가 없는 기존 시작을 유지한다.
- 하나의 `.verison-list` positional argument를 UTF-8 원문 그대로 보존한다.
- renderer option의 전후 순서를 허용하고 확장자는 대소문자를 구분하지 않는다.
- 중복 positional path, 다른 확장자, backup suffix와 trailing-space suffix를 거부한다.

CTest 54개는 Catch2 단위 및 통합 test 48개, asset checksum 1개, source style 1개와 renderer smoke test 4개다. 저장 실패 경로는 in-memory fake로 결정적으로 주입했고 실제 Win32 임시 디렉터리 통합 test로 생성, 교체, 외부 변경과 replace 실패 정리도 검증했다.

VS2026 build는 sandbox FileTracker가 `E_ACCESSDENIED`를 반환하는 기존 호스트 제약 때문에 같은 preset을 host 권한에서 실행했다. build와 CTest 결과에는 실패가 없었다.

## 6. aggregate format 기준선 해소

이전 test 체크포인트에서 현재 변경 범위 밖으로 보류했던 다음 세 파일의 clang-format 19.1.5 위반을 `S2-V1`에서 프로젝트 formatter로만 정렬했다.

- `src/platform/win32/utf8.cpp`
- `src/platform/win32/win32_application.cpp`
- `src/presentation/ui_theme.h`

변경은 줄바꿈, 인자 배치와 formatter가 요구하는 `case` scope 배치뿐이며 동작 변경은 없다. 보정 후 VS2022 Debug/Release, `/analyze`, VS2026 Debug와 양 toolchain 전체 CTest를 다시 실행했고 모두 통과했다. aggregate `gitman_format_check`도 최종 통과했다.

## 7. 보류 및 후속 단계 경계

- symlink, junction, Git worktree와 bare repository의 실체 동일성 판정은 단계 5 범위다.
- 문서가 없는 시작의 새 문서 및 열기 UI와 실제 활성 document app state 연결은 단계 6 범위다.
- `.verison-list` Windows file association 등록 및 제거는 단계 8 범위다.
- Git/SVN command 실행과 provider는 각각 단계 3과 4에서 구현한다.
- 단계 1 custom caption 수동 검수 체크리스트의 미확인 항목은 단계 2 자동 검증과 별개로 계속 보존한다.
- ADR-004의 범용 메시지 구조는 단계 6 전 별도 설계 승인 없이는 구현하지 않는다.
