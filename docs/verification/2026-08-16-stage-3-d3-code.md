# 단계 3 `S3-D3-CODE` 검증 기록 - 2026-08-16

## 1. 결과

활성 code page fallback transcoder를 구현하고 출력 파이프라인에 연결했다. `process_text_encoding::active_code_page_fallback`을 요청하면 UTF-8로 해석되지 않는 레코드만 활성 code page로 다시 해석한다.

출력 pipe, reader 스레드와 줄 단위 레코드는 사용자 지시로 `S3-D2-CODE`에서 이미 구현했으므로 이번 구간에는 인코딩 fallback만 남았다.

VS2022 Debug/Release와 VS2026 Debug build가 통과했고 기존 전체 CTest가 각 107/107 통과했다. VS2022 `/analyze`는 경고 없이 통과했다. 새 test source는 작성하지 않았고, 저장소 밖 임시 프로그램으로 활성 code page 949 환경에서 15개 항목을 수동 확인했다. 상세는 5장에 있다.

## 2. 구현 범위

### 2.1 transcoder 경계

`src/application/text_transcoder.h`는 구현 없는 추상 계약이다.

- `to_utf8(bytes)`는 변환 결과를 돌려주고, 변환할 수 없으면 값을 돌려주지 않는다.
- 입력은 UTF-8이 아닌 raw byte지만 저장소 계층과 같은 이유로 `std::u8string_view`에 담아 전달한다. 실제 code page 해석은 Win32 adapter만 수행하므로 상위 계층에 Windows type이 노출되지 않는다.
- `noexcept` 계약이므로 변환 실패를 예외가 아니라 값으로 보고한다.

`src/platform/win32/win32_text_transcoder.h/.cpp`가 `CP_ACP` 구현을 제공한다.

| 항목 | 구현 |
| --- | --- |
| 변환 | `MultiByteToWideChar(CP_ACP, MB_ERR_INVALID_CHARS, ...)`로 UTF-16을 만든 뒤 기존 `utf16_to_utf8`로 되돌린다. |
| 실패 처리 | `MB_ERR_INVALID_CHARS`를 지정해 활성 code page에서도 해석할 수 없는 byte가 있으면 실패로 만든다. 호출자가 U+FFFD 대체로 되돌릴 수 있어야 하기 때문이다. |
| 빈 입력 | 빈 문자열을 그대로 돌려준다. |
| 크기 한계 | `int` 범위를 넘는 입력은 변환하지 않는다. |
| 상태 | 상태를 갖지 않으므로 두 reader 스레드가 같은 instance를 함께 사용할 수 있다. |
| 예외 | 내부 할당 실패를 흡수해 `noexcept` 계약을 지킨다. |

### 2.2 파이프라인 연결

`process_output_pipeline`이 인코딩 모드와 transcoder 포인터를 함께 받는다. 두 인자는 기본값이 있어 기존 호출과 test는 그대로 동작한다.

레코드 텍스트를 만들 때 다음 순서로 판단한다.

1. 모드가 `utf8`이면 항상 UTF-8로 해석하고 잘못된 byte만 U+FFFD로 대체한다.
2. 모드가 `active_code_page_fallback`이고 레코드가 유효한 UTF-8이면 그대로 둔다. 정상 출력이 code page 해석으로 훼손되지 않게 하기 위해서다.
3. 유효한 UTF-8이 아니고 transcoder가 있으면 활성 code page로 변환한다. 성공하면 `transcoded_from_active_code_page`를 세운다.
4. 변환이 실패하면 U+FFFD 대체로 되돌리고 `replaced_invalid_bytes`를 세운다.

판단 단위는 레코드 하나다. 따라서 한 실행 안에서 UTF-8 줄과 code page 줄이 섞여도 각각 알맞게 처리된다.

유효성 판정을 위해 `is_valid_utf8_text`를 공개했다. overlong, surrogate, U+10FFFF 초과와 미완결 sequence를 모두 거부하므로 `normalize_utf8_text`와 같은 기준을 사용한다.

### 2.3 runner 연결

- transcoder는 `active_code_page_fallback`을 요청한 실행에서만 만든다. 기본 경로에는 추가 비용이 없다.
- 두 스트림 파이프라인이 같은 transcoder instance를 공유하며 `run`이 반환할 때 함께 해제된다.
- reader 스레드는 `run` 반환 전에 항상 join되므로 transcoder 수명이 스레드보다 먼저 끝나지 않는다.

### 2.4 build 구성

`application/text_transcoder.h`와 `platform/win32/win32_text_transcoder.*`를 `gitman_process`에 추가했다. runner와 같은 이유로 target을 나누지 않는다.

## 5. 저장소 밖 수동 확인

활성 code page가 949인 이 호스트에서 임시 확인 프로그램을 만들어 실행했다. 자식은 저장소 build tree의 `gitman_process_test_child.exe`를 그대로 사용했고 확인 프로그램은 삭제했다.

| 항목 | 결과 |
| --- | --- |
| 프로세스 활성 code page가 949로 보고됨 | 통과 |
| `utf8` 모드에서 CP949 byte가 U+FFFD로 대체되고 transcode 표시가 없음 | 통과 |
| fallback 모드에서 CP949 byte가 `한글`로 복원되고 transcode 표시가 세워짐 | 통과 |
| fallback 모드의 복원 결과에 대체 표시가 없음 | 통과 |
| 한 실행에서 CP949 줄은 변환되고 UTF-8 줄은 그대로 유지됨 | 통과 |
| CP949에서도 해석할 수 없는 `0xFF`가 U+FFFD로 대체되고 transcode 표시가 없음 | 통과 |
| fallback 모드에서도 정상 UTF-8 출력이 변형 없이 전달됨 | 통과 |

## 6. 구현 중 검토 결과

- 실행 파일 manifest에 `activeCodePage` 설정이 없으므로 프로세스 활성 code page는 시스템 설정을 따른다. 이 호스트에서는 949이며, UTF-8 code page를 쓰는 환경에서는 fallback이 자연스럽게 무해한 no-op이 된다.
- 유효한 UTF-8을 먼저 확인하고 실패한 레코드만 변환하는 순서를 택했다. 반대로 항상 code page로 해석하면 정상 UTF-8 출력이 깨진다.
- `MB_ERR_INVALID_CHARS`를 빼면 해석할 수 없는 byte가 조용히 대체 문자로 바뀌어 U+FFFD 경로와 구분되지 않는다. 그래서 엄격 변환을 유지하고 실패를 상위 계층에 알린다.
- 현재 알려진 production 결함은 없다. 전용 test는 체크포인트 분리 규칙에 따라 아직 작성하지 않았다.
