## 2. 구현 경계와 설계 대비 차이

설계 문서 "설계에서 달라진 것"을 모은다. 요점:

- **luil은 바꾸지 않았다.** luil에 없던 것(사라진 초점을 넘기는 hook, live region 알림, 소비한 Alt 조합 삼키기 등)은 gitman 쪽에서 우회하거나 "확인하지 못한 것"에 luil 요청 후보로 적었다.
- **계층**: 모델·치환·신뢰 해시(SHA-256 순수 C++)·편집 규칙은 domain, 실행 풀·intent 처리는 application(`logic_controller`와 `logic_function_editor.cpp`), 요청 조립·인용·비밀 가리기·forwarder는 infrastructure, 분리 실행기·환경 블록은 platform, 카드 열·기능 줄·dialog는 presentation이다. UI thread는 파일·프로세스 I/O를 하지 않는다(ADR-004).
- **설계를 구체화하거나 좁힌 곳**(모두 설계 문서에 근거): 분리 실행은 새 `process_launch_request`·`process_launcher`(T4), 값이 없는 `GITMAN_*`는 물려받은 같은 이름을 지움(T4), 풀 상한은 대기 + 실행 중 수(T5), `Alt+N`은 policy가 아니라 logic이 새 intent `run_function_shortcut_intent`로 풂(T9), 경과 시간은 3번째 줄 칩에서만 흐름(T9·T10), 창 닫기는 luil `ui_frame::close` 훅으로 가로챔(T11), 편집 dialog 저장 뒤 신뢰 갱신은 편집 전에 신뢰했고 이어 낼 저장이 없을 때만(T12, D24-A).
- **V에서 바뀐 동작**: 편집 dialog의 Apply가 바꾼 정의는 저장될 때까지 실행하지 않음, cmd 방어 문자에 `!`, 다른 문서를 열면 편집 dialog 등을 바로 닫음, 같은 아이콘 card 기능 경고(5장).
- **빌드**: MSVC 공용 옵션에 `/bigobj`(T11, 사용자 확인 대기).
- `docs/user-manual.html`은 고치지 않았다(2026-09-06 뒤로 md와 맞추지 않은 상태 그대로).

관찰(결함으로 판정하지 않음, 고치지 않음):

- **실행 중 업데이트·전환 버튼이 UIA tree에서 사라진다.** 비활성일 때 클릭 동작을 달지 않고(`card_element.cpp:229-245`) luil이 동작 없는 요소를 접는 것으로 추정한다. 그래서 비활성 사유 tooltip(`기능 "핑20"이 실행 중입니다`)이 낭독기에 닿지 않는다. 비활성 card 기능 버튼은 `IsEnabled=False`로 남는다. 이 방식은 기준점부터 있었다. 선택이 없을 때 기능 줄의 비활성 `⋯`가 tree에 없는 것도 같은 모양이다.
- **로그 줄이 UIA에 노출되지 않는다.** `log_view_element`에 접근성 정보가 없다(이 브랜치에서 바뀌지 않은 파일). 기능 버튼 로그도 낭독기로 읽을 수 없다.
- **편집 dialog 아이콘 줄에서 `재생`과 `디버그 시작` 글리프가 거의 같아 보인다.** 보기 문제다. (5차 검수에서 고치기로 골라 S2에서 고침: 이름은 그대로 두고 `debug-start`를 codicon `debug-alt` 글리프로 그린다.)
- **파일 로그 머리글 `# 문서:`에 문서 경로가 아니라 로그 폴더 경로가 찍힌다**(`file_log_writer.cpp:234`). 기능 버튼과 무관하고 이 브랜치에서 바뀌지 않았다. (5차 검수에서 고치기로 골라 S3에서 문서 경로로 고침.)

이 단계에서 결함을 찾지 못해 코드를 고치지 않았다. 그래서 전체 CTest를 다시 돌리지 않았다(3장의 결과가 최종 코드 기준).

점검 뒤 `gitman.app-settings.json`을 점검 전 사본으로 되돌렸다(SHA-256이 원본과 같음). 카드의 업데이트·전환은 누르지 않았고 repo-a·repo-b는 `git status`가 깨끗하다.

## 7. 남은 위험

- **종료 직전 대기 저장이 버려진다.** 앞선 저장이 진행 중일 때 낸 저장(`save_queued_`: 편집 dialog Apply, 배치 변경, 카드 순서 변경)을 `begin_shutdown`이 보지 않는다. 고치려면 진행 중 저장의 결과 revision으로 이어 쓰거나 runtime 종료 순서를 바꿔야 한다. 기준점의 카드 순서 변경·창 배치 저장에도 있던 틈이다.
- **앱 설정을 읽기 전에 누른 기능은 이미 신뢰한 정의도 다시 묻는다.** T7이 읽기 전 신뢰를 합쳐 저장하기로 정했고 그것을 고정하는 test(`A trust recorded before the app settings arrive survives the load and is saved`)가 있어 두었다. - **Debug 타이밍 test가 부하 중 드물게 출력 없이 끝난다**(약 90회 중 2회, 원인 미확정, 3장). (5차 검수에서 고치기로 골라 S5에서 다시 봄: 재현된 간헐 실패는 단언 실패 셋과 출력이 멎은 멈춤 하나였다. 단언 실패는 test를 고쳤고, 멈춤은 파일 로그 writer의 경쟁이라 제품을 고쳤다. V의 종료 코드 127 그대로는 재현되지 않았다, 11장.)

### 9.2 정한 규칙

- **R1 (D26·D27, 설계 3.3·3.5·3.6·4.3, 설명서 12.6·12.7)**
  - `program`이 `cmd.exe`이면 gitman이 명령줄을 `/d /s /c "…"` 한 묶음으로 따로 짓고, 인자의 `& | < > ^ ( )` 등을 `^`로 보정해 넘긴다. `D:\R&D\…`·`OneDrive - 회사명` 같은 문서 경로가 그대로 닿는다. 표시용 명령줄도 같은 조립을 쓴다.
  - 보정할 수 없는 `% ! "`·CR·LF가 든 값은 출처와 상관없이 실행하지 않는다. (R4에서 D30으로 `% ! "`도 보정하고 줄바꿈만 거부하게 바뀜, 10장)
  - 배치가 읽을 런타임 `GITMAN_BRANCH`·`GITMAN_REPOSITORY_ROOT`에 cmd 메타 문자(`, ; =` 포함, 공백·탭은 뺌)가 있으면 실행하지 않고 로그를 한 줄 남긴다. 설명서의 권장 예는 `"%GITMAN_BRANCH%"`다. (R4에서 D30으로 거부를 경고와 사용자의 최종 승인으로 바꿈, 10장)
  - 검토 반영: argv[0]의 `/`는 `\`로 바꿔 쓴다(`C:/…/cmd.exe`가 `/c`로 읽혀 `md`가 돌던 것). `/c:x`·`/K:1`·`/r:x`는 스위치가 아니라 명령의 시작으로 본다.
  - 공백이 든 명령 한 덩어리(`["/c","echo hi"]`)는 실패하므로 명령과 인자를 나눠 적는다(동작 변경). (R4에서 D30으로 명령 문장으로 넘겨 다시 동작함, 10장)
- **R2 (D28, 설계 4.9·4.10·4.11, 설명서 5장·12.9·18장)**
  - logic이 저장하지 못한 변경(`unsaved_`: 문서, 기능 정의)을 기억하고, 그 상태의 다시 읽기·문서 닫기·다른 문서 열기·종료 전에 실행 중인 기능 확인과 같은 dialog로 묻는다. 진행 중이거나 대기 중인 저장이 있는 동안은 묻지 않는다.
  - 저장 충돌 알림: `문서가 밖에서 바뀌어 저장하지 않았습니다. 문서 다시 읽기로 불러오십시오.`
  - 검토 반영: 탐색 후보 등록이 성공하면 문서 표시를 끈다(기능 정의 표시는 남김). 열린 확인 dialog는 그 뒤 실패한 저장을 싣도록 다시 짓고, 기다리던 다시 읽기는 다른 확인 dialog를 덮지 않는다. 변경만 있는 dialog는 높이를 줄이고, "사라집니다" 문구는 경고 줄로 그린다.

### 9.4 남은 것

설계 문서 "확인하지 못한 것"의 (R1, 남김)·(R1 검토, 남김)·(R2, 남김)·(R3, 남김)이 정본이다. 요점:

- **사용자 확인 필요**(8장에 더함): 공백이 든 명령 한 덩어리 cmd 정의가 R1부터 실패, `!`가 든 폴더 경로를 넘기는 cmd 기능도 막힘, 저장소 루트에 `& ( ) , ; =` 등이 있는 카드의 cmd 기능이 모두 거부됨, 손 편집·pull로 `placement`를 바꿔 `Alt+1~3` 대상이 바뀌어도 다시 묻지 않음. (앞의 셋은 4차 검수 D30으로 결정해 R4에서 반영, 10장)
- **값이 그대로 닿지 않는 경우**: 감싼 인자 끝의 `\`는 배치의 `%~1`에 둘로 보이고, 배치가 `call`을 쓰면 따옴표 안 `^`가 두 배가 된다. `${svnUrl}`·`${env:}`·사용자 변수는 환경 변수 검사가 없어 배치가 따옴표 없이 `%~1`로 읽으면 `&`가 명령이 된다(설명서는 `"%~1"`을 권함). 래퍼 exe가 배치를 부르는 경로는 `program` 판정으로 잡지 못한다.
- **저장 진행 중의 틈**: 저장이 진행 중일 때 닫기·다른 문서 열기·종료를 하면 묻지 않고, 그 저장이 실패하면 변경이 말없이 사라진다(V 남김 항목과 같은 틈). 쓰기 실패 상태에서 `버리고 닫기`·`버리고 종료`를 골라도 창 배치 저장이 그 변경을 파일에 남길 수 있다(해롭지 않은 쪽).
- **신뢰**: R3 전 신뢰는 한 번 다시 묻는다. `vcs_hint`는 여전히 해시 밖이다.
- **앱에서 보지 못한 것**: 분리 실행(`detached`)의 cmd 조립을 실제 창으로 띄우지 않음. 레지스트리 `DelayedExpansion`·`AutoRun`이 켜진 기계, 다른 Windows 판·코드 페이지. R2 확인 dialog는 `문서 닫기`의 변경만 있는 모양 하나만 어두운 테마·기본 글 크기로 봄(다시 읽기·다른 문서 열기·종료, 실행 중 기능과 함께 뜨는 모양, 글 크기 150%, 밝은 테마·고대비는 test로만). R3의 이름 변경 뒤 다시 묻는 흐름은 test로만 봄. 이번 재검증은 앱 점검을 다시 하지 않았다.
- **Debug 타이밍 test**(3장): 이번 Debug 전체 실행은 다른 빌드 없이 돌려 실패가 없었다. 원인은 여전히 확정하지 못했다.

| 거부 | 줄바꿈(CR·LF)만 |

- **신뢰 dialog의 버튼 다섯이 모두 UIA에 나오는지 확인하지 못했다.** 처음 화면에 넷, (6) 화면에 셋만 보였다. 목록이 보이는 항목만 짓는 것으로 보이며 R4 범위 밖이라 더 보지 않았다.

### 10.5 남은 것

설계 문서 "확인하지 못한 것"의 (R4, 남김)이 정본이다. 요점:

- **사용자 확인 필요**(8장): 손 편집·pull로 `placement`를 바꿔 `Alt+1~3` 대상이 바뀌어도 다시 묻지 않음(R3에서 남은 것, 5차 검수 D31로 결정해 S1에서 고침: 보이는 `card`와 그 순서가 해시에 들어 손 편집·pull로 `Alt+N` 대상이 바뀌면 다시 묻는다). 그 밖의 설계 재검수·사용자 확인 항목은 8장 그대로다.
- **cmd 한계**: 부른 배치가 `setlocal EnableDelayedExpansion`을 켜면 넣은 `/v:off`가 무력해진다(설명서 12.6에 적음, 막지 않음. S3에서 명령이 부르는 배치에 그 줄이나 `call`이 있으면 경고하게 함). `call`로 `%`가 든 값을 넘기면 인자 경계가 바뀌거나 실행되지 않을 수 있다(주입은 확인하지 못함). `CommandLineToArgvW` 규칙의 프로그램은 `""` 뒤 공백에서 인자를 가를 수 있다. `unprotected_value` 경고는 사용자가 그래도 승인할 수 있다(원인은 작성자의 문장).
- **문장 판정**(공백이 든 상대 경로는 S3에서 작업 폴더에 그 파일이 있는지로 가르게 고침): 공백이 든 상대 경로와 실행 확장자 이름이 든 폴더(`C:\my.bat files\x.exe`)는 문장으로 잘못 볼 수 있다(확인 dialog에 보임). `${tool} --flag`처럼 변수로 시작하는 문장에서 그 값에 공백이 있는 경우는 실제 `cmd.exe`로 돌려 보지 않았다(R4에서 새로 깨진 경우는 아님).
- **앱에서 보지 못한 것**: 확인 dialog의 `Esc`·창 밖 클릭 취소, 분리 실행의 cmd 조립, 레지스트리 `DelayedExpansion`이 켜진 기계, 글 크기 150%·밝은 테마·고대비에서의 경고색. 10.4의 기록만 한 세 가지.
- **`[runner]` test**: R4 첫 구현 때 한 번 실패했고 그 뒤 두 번과 이번 전체 실행에서는 통과했다. 원인을 모른다. 3장의 Debug 타이밍 test와 같은 것인지도 확인하지 못했다. (S5에서 가름: 다른 원인이다. 자식을 만든 때부터 재는 짧은 제한 시간(400ms) 안에 부하 중 Debug 자식이 첫 줄을 쓰지 못하거나 경고 진단이 첫 자리에 서서 단언이 실패한다. test를 고쳤다, 11장.)

### 12.5 사용자 수동 확인 절차

시스템 설정을 바꾸거나 귀로 들어야 해서 점검이 하지 못한 것이다. 끝나면 바꾼 설정을 되돌린다.

1. **conhost 기본 터미널**: 설정 > 시스템 > 개발자용 > 터미널을 `Windows 콘솔 호스트`로 바꾼다. 분리 실행 기능(`mode: detached`의 짧은 cmd)을 실행해 conhost 창이 뜨고 끝나면 닫히는지, 로그에 `[…] 시작:` 한 줄만 남는지 본다.
2. **고대비**: 설정 > 접근성 > 대비 테마에서 하나를 적용한다. `⋯`의 실패 마름모와 실행 중 원이 버튼 테와 구별되는지, 비활성 버튼과 확인 창의 경고 줄이 보이는지 본다.
3. **텍스트 크기 150%**: 설정 > 접근성 > 텍스트 크기를 150%로 하고 앱을 다시 띄운다. 코드로는 변화가 없을 것으로 본다(12.4). 글이 커지기를 기대한다면 그 자체가 결함이다(luil 요청 후보).
4. **내레이터**(`Ctrl+Win+Enter`): Tab으로 카드 `⋯`에 가서 "기능 더 보기, … 실패 1개"를 읽는지, 실행 중 업데이트 버튼을 "사용할 수 없음"과 사유(HelpText)와 함께 읽는지, 로그 목록의 줄을 읽는지, 기능 줄 버튼이 `· 실행 중`으로 바뀔 때와 실행이 끝나 버튼이 다시 켜질 때 알림이 있는지 듣는다.
5. **경고음**: 앱이 맨 앞 창일 때 실제 키보드로 `Alt+1`과 `Alt+↓`를 누르고 `Alt`를 뗄 때 "띵" 소리가 나는지 듣는다.

### 12.6 남은 것

설계 문서 "확인하지 못한 것"의 S1~S6·S 항목이 정본이다. 다음에 할 일(D32 UIA Invoke의 고칠 길, 사용자 수동 확인, luil 요청 후보, 후속 기능)은 handoff 0.2.1 "다음에 할 일" 한 곳에 모았다. 요점:

- **실제 앱에서 보지 못한 것**: 종료의 5초 상한과 `문서 저장 중` 창, 고대비, 낭독, 경고음, conhost(12.5).
- **luil이 있어야 고칠 것**: 1366×768을 175% 이상으로 쓰는 등 작업 영역이 433보다 낮으면 카드 메뉴 아래가 잘림(메뉴 스크롤), 저장이 성공해도 `종료`를 한 번 더 눌러야 함(logic이 앱을 끝낼 길), 흐르는 로그의 끝 맞추기(UIA Scroll 패턴), 막힌 버튼의 상태 변경 알림, D32의 UIA Invoke, Windows 텍스트 크기.
- **S3 한계**: 5초를 넘겨 끝내거나 로그오프로 끝나면 진행 중 저장의 결과를 보지 못한다(runtime 종료 순서). 신뢰한 문서의 닿지 않는 UNC 배치는 5초 뒤 logic은 풀리지만 조회 worker가 붙잡힌다. `NoDefaultCurrentDirectoryInExePath`가 켜진 기계의 경로 없는 `run.bat`, 8.3 이름·UTF-16 배치는 정확히 보지 못한다.
- **S5**: 200회 P2 부하는 test만 고친 실행 파일로 돌렸다. 이제 Debug CRT assert도 `0xC0000409`로 끝나므로 표준 오류의 `Assertion failed`를 먼저 본다.
