### 2.1 차단 사유 matrix

`evaluate_git_update_preflight`는 순수 함수라 프로세스 없이 전수 확인한다.

| 확인 | 기대 |
| --- | --- |
| 저장소 아님, 충돌, 진행 중 작업, `index.lock`, detached, dirty, **미상**, diverged | 각각 대응하는 차단 사유 |
| `behind`, `up_to_date`, 원격 미확인(`unknown`) | 통과. update가 존재하는 이유인 상태다 |
| 사유 5개 동시 발생 | 충돌 → 진행 중 작업 → `index.lock` → detached → diverged 순으로 하나씩 사라질 때마다 다음 사유를 돌려준다 |

submodule 사전 검사는 정상·미초기화 통과, 충돌·커밋 불일치 차단, 섞여 있으면 차단을 단정한다.

provider 층에서는 fake runner로 차단 4종(dirty, 충돌, detached, diverged)과 진행 중 작업, 도구 부재, 대상 없음 2종을 확인하며 **모든 경우에 `pull` 명령이 0개**임을 단정한다.

### 2.2 실행 경로

| test | 단정 |
| --- | --- |
| 성공 | 요청 6개, 순서가 조회 2 → `remote` → `pull` → 재조회 2, pull의 마지막 인자가 branch |
| fast-forward 실패 | `executed`는 참, `succeeded`는 거짓, **실패해도 사후 재조회 수행** |
| 인증 실패 | 한국어 메시지에서 `authentication_required`로 분류 |
| timeout | `blocked_by`는 `none`이고 `process_timed_out` 진단. 차단과 실패는 다른 개념이다 |
| submodule off | `submodule` 명령 0개, pull 인자가 `--recurse-submodules=no` |
| submodule on | 요청 8개, 순서가 조회 2 → `remote` → `submodule status` → `pull`(on-demand) → `submodule update` → 재조회 2 |
| 위험한 submodule | `pull` 0개, `submodule` 1개(조사만), 조사 결과는 snapshot에 담김 |
| pull 실패 후 | `submodule` 1개. 갱신을 실행하지 않는다 |
| submodule 갱신 실패 | 전체 `succeeded`가 거짓 |

SVN도 같은 방식으로 차단(dirty에서 `update` 명령 0개), 성공(조회 7 + update 1 + 재조회 7), 실패 후 재조회, 도구 부재를 단정한다.

### 2.3 실제 Git 통합 test

| test | 확인 |
| --- | --- |
| 뒤처진 저장소 | **실제로 fast-forward됨.** 사후 재조회가 `up_to_date`와 clean을 보고 |
| 이력이 다시 쓰인 원격 | 원격을 force-push로 다시 쓰고 로컬 tracking ref는 옛 값이라 사전 검사를 통과한다. `pull --ff-only`가 **merge를 만들지 않고 실패**하며 작업 트리는 그대로 clean |
| dirty, diverged, detached, remote 없음 | 각각 대응하는 사유로 차단 |
| 실제 submodule | off면 `submodules`가 비고, on이면 조사 결과 1개(`vendor/모듈`)가 담기며 갱신 후에도 작업 트리가 clean |

두 번째 test가 이 구간에서 가장 중요한 확인이다. 사전 검사만으로는 걸러지지 않는 경우에 `--ff-only`가 마지막 방어선으로 동작하는 것을 실제 Git으로 보여 준다.

## 3. test 작성 중 확인한 것

production 결함은 없다. 다음 세 가지를 확인했다.

1. **`repository_change_result`에는 `has_errors()`가 없다.** `repository_query_result`에만 있다. 실행 결과는 `executed`와 `succeeded`로 성패를 나타내므로 의도된 비대칭으로 보고 test에서 진단을 직접 확인했다. 단계 6에서 카드가 두 결과를 함께 다룰 때 다시 볼 항목이다.
2. **`svnversion` 요청에는 인자가 하나도 없다.** 처음에 `arguments.back()`으로 확인하다가 빈 vector에 접근해 test가 죽었다. 인자 목록 전체를 보도록 고쳤다. production은 그대로다.
3. **Git은 기본 설정에서 submodule을 `file` 경로에서 받아 오지 않는다.** 실제 submodule 통합 test에서 `submodule update --init`이 원본을 새로 clone하려다 막혔다. production이 `protocol.file.allow`를 만들지 않는 것은 옳으므로, 준비 단계에서 `clone --recurse-submodules`로 미리 초기화해 production 명령이 clone할 필요가 없게 했다. 실제 사용 환경의 submodule 원본은 https나 ssh다.
