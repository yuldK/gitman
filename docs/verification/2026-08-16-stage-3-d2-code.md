# 단계 3 `S3-D2-CODE` 검증 기록 - 2026-08-16

## 1. 결과

셸을 거치지 않는 프로세스 시작 계약과 출력 수집을 구현했다. `CommandLineToArgvW` 규칙 인자 인용, `CreateProcessW` 시작, 작업 디렉터리와 환경 적용, stdin `NUL` 연결, 상속 handle 제한, pipe별 reader 스레드, 줄 단위 레코드, 종료 코드 수집과 시작 실패 보고가 동작한다.

첫 제출에서는 출력을 `NUL`로 버리고 wait 실패 시 자식을 남겼다. 사용자 검수 결과에 따라 다음 두 항목을 반영해 다시 제출한다.

1. wait 실패 시 자식을 정리하고 `exited` 대신 전용 실패 상태로 보고한다.
2. `S3-D3-CODE`로 미뤘던 출력 pipe와 reader 스레드를 이번 구간에 포함한다.

timeout과 취소는 `S3-D4-CODE`, 마스킹은 `S3-D5-CODE` 범위이므로 여전히 포함하지 않았다. 활성 code page fallback transcoder만 `S3-D3-CODE`에 남는다.

VS2022 Debug/Release와 VS2026 Debug build가 통과했고 기존 전체 CTest가 각 78/78 통과했다. VS2022 `/analyze`는 경고 없이 통과했다. 새 test source는 작성하지 않았고, 대신 저장소 밖 임시 프로그램으로 시작 계약 21개와 출력 34개 항목을 수동 확인했다. 상세는 5장에 있다.

## 2. 구현 범위

### 2.1 인자 인용

`src/infrastructure/command_line_builder.h/.cpp`는 OS API 없이 명령줄 문자열을 만든다.

| 규칙 | 구현 |
| --- | --- |
| 인용 필요 판정 | 공백, tab, 개행, 수직 tab, 따옴표를 포함하거나 빈 인자일 때만 감싼다. |
| 따옴표 | 인자 내부 `"`는 앞선 backslash를 두 배로 늘린 뒤 `\"`로 쓴다. |
| 닫는 따옴표 앞 backslash | 두 배로 늘려 문자로 남긴다. |
| 빈 인자 | `""`로 만들어 사라지지 않게 한다. |
| 셸 metacharacter | `&`, `|`, `^`, `>`는 특별 처리하지 않고 값의 일부로 남긴다. |
| argv[0] | backslash 이스케이프 규칙이 없으므로 실행 파일 경로를 그대로 감싼다. 실제 실행 대상은 `lpApplicationName`이 결정하므로 argv[0]은 표시용 값이다. |

### 2.2 프로세스 시작

`src/platform/win32/win32_process_runner.h/.cpp`가 `process_runner`를 구현하고 `make_process_runner()`로 instance를 제공한다.

| 항목 | 구현 |
| --- | --- |
| 실행 대상 | `lpApplicationName`에 절대 경로를 넘겨 PATH 탐색과 확장자 추론을 사용하지 않는다. |
| separator | 실행 파일과 작업 디렉터리의 `/`를 `\`로 바꿔 `\\?\` 경로에서도 안전하게 만든다. |
| 명령줄 | `CreateProcessW`가 buffer를 수정할 수 있으므로 쓰기 가능한 사본을 넘긴다. |
| flag | `CREATE_NO_WINDOW`, `CREATE_UNICODE_ENVIRONMENT`, `EXTENDED_STARTUPINFO_PRESENT`를 사용한다. 셸을 실행하지 않는다. |
| stdin | 항상 `NUL` handle이므로 자식이 프롬프트를 읽으면 즉시 EOF가 된다. |
| stdout/stderr | 각각 익명 pipe다. 쓰기 end만 상속 가능하게 만들고 읽기 end의 상속 flag는 지운다. |
| handle 상속 | `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`로 세 표준 handle만 상속시켜 다른 handle 누출을 막는다. |
| handle 정리 | 시작 직후 부모의 쓰기 end 사본을 닫는다. 닫지 않으면 자식이 끝나도 reader가 EOF를 관측하지 못한다. |
| 종료 코드 | `WaitForSingleObject` 후 `GetExitCodeProcess` 결과를 bit 값 그대로 `std::int32_t`로 보존한다. `0xC0000005` 같은 상위 bit 코드가 손실되지 않는다. |
| 시간 | 표시용 시각은 `system_clock`, 경과 시간은 `steady_clock`으로 각각 측정한다. |
| 시작 실패 | `CreateProcessW` 실패를 `start_failed`와 Win32 error code, 구조화 진단으로 보고한다. |
| 잘못된 요청 | `validate_process_request` 오류가 있으면 프로세스를 만들지 않고 `invalid_request`로 반환하며 명령줄도 기록하지 않는다. |
| 예외 | 모든 실패를 값으로 반환하고 `run`은 `noexcept`를 지킨다. 진단 문자열 할당 실패까지 흡수한다. |

### 2.2.1 실패 정리와 `internal_error`

프로세스는 시작했지만 결과를 신뢰할 수 없는 경로를 `process_completion::internal_error`로 새로 구분했다. 세 경로 모두 자식을 남기지 않는다.

| 경로 | 처리 |
| --- | --- |
| reader 스레드 생성 실패 | 자식을 즉시 종료하고 이미 만든 스레드를 join한 뒤 `internal_error`와 `process_pipe_failed` 진단을 반환한다. reader 없이 두면 자식이 pipe buffer에서 막힌다. |
| `WaitForSingleObject` 실패 | 자식을 `TerminateProcess`로 정리한다. 그래야 orphan이 남지 않고 pipe가 닫혀 reader 스레드가 끝난다. 이후 `internal_error`와 Win32 error code를 반환한다. |
| `GetExitCodeProcess` 실패 | 종료 코드를 비운 채 `internal_error`로 보고한다. |

이전 제출은 이 세 경로를 `exited`로 보고하고 wait 실패 시 자식을 그대로 두었다. `succeeded()`는 `exited`만 성공으로 보므로 결과 판정 자체는 안전했지만, 완료 사유가 사실과 달랐고 자식이 orphan으로 남을 수 있었다.

### 2.2.2 출력 수집

- pipe마다 전용 reader 스레드를 둔다. 한 스레드로 두 pipe를 읽으면 읽지 않는 pipe의 buffer가 가득 차 자식이 멈춘다.
- 읽기 단위는 `process_read_block_byte_size`(64 KiB)다.
- `ReadFile` 실패(`ERROR_BROKEN_PIPE` 포함)와 0 byte 반환을 EOF로 보고 스레드를 끝낸다.
- 두 스레드는 `run`이 반환하기 전에 항상 join된다. detach하지 않는다.
- `output_collector`가 mutex 아래에서 실행 단위 sequence를 부여하고 sink를 호출한다. sink 구현은 스스로 동기화하지 않아도 되고, 같은 스트림의 상대 순서는 항상 보존된다.
- sink가 예외를 던지면 reader 스레드를 종료시키지 않고 흡수한 뒤 결과에 진단으로 남긴다. 예외로 reader가 죽으면 자식이 pipe에서 막히기 때문이다.
- `sink`가 null이어도 pipe를 계속 비우고 레코드 수와 캡처 byte를 집계한다.

### 2.2.3 줄 단위 레코드와 인코딩

`src/infrastructure/process_output_pipeline.h/.cpp`가 스트림별로 byte를 레코드로 바꾼다. reader 스레드 하나가 단독 소유하므로 내부 잠금이 없다.

| 규칙 | 구현 |
| --- | --- |
| 줄 끝 | `\r\n`과 `\n`은 줄의 끝이다. |
| 진행 표시 | 단독 `\r`도 줄 끝으로 처리하고 `progress`를 세운다. 내용이 없는 진행 표시는 레코드를 만들지 않는다. |
| 빈 줄 | `\n`으로 끝난 빈 줄은 그대로 보존한다. |
| 강제 분할 | 줄 끝 없이 `maximum_record_bytes`에 도달하면 끊고 `continued`를 세운다. |
| UTF-8 경계 | 강제 분할 위치가 multi-byte sequence 내부면 sequence 시작으로 되돌려 다음 레코드로 넘긴다. 요청 검증이 최소 4 byte 상한을 보장하므로 어떤 sequence도 항상 한 레코드에 들어간다. |
| chunk 경계 | 줄이 완성될 때까지 buffer에 모으므로 읽기 경계에 걸친 문자도 깨지지 않는다. |
| 잘못된 byte | overlong, surrogate, U+10FFFF 초과와 미완결 sequence를 U+FFFD로 대체하고 `replaced_invalid_bytes`를 세운다. |
| 캡처 상한 | 스트림별 상한까지만 수집하고 남은 pending을 내보낸 뒤 `truncated`를 세운다. 이후 byte는 버리지만 pipe는 계속 비운다. |
| 절단 보고 | 절단이 발생하면 결과에 `process_output_truncated` warning 진단을 남긴다. 실행 자체는 실패로 보지 않는다. |

### 2.3 환경 적용

- override가 없으면 `lpEnvironment`에 `nullptr`을 넘겨 부모 환경을 그대로 상속한다.
- override가 있으면 부모 환경을 읽어 항목별로 덮어쓰거나 삭제한 뒤 새 block을 만든다.
- 이름 비교는 `CompareStringOrdinal`의 대소문자 무시 비교다. Windows 환경 변수 이름 규칙과 일치한다.
- `=C:` 형태의 drive 현재 디렉터리 항목은 이름이 `=`로 시작하므로 구분자를 index 1부터 찾아 보존한다.
- `CreateProcess`가 요구하는 대로 이름 기준 대소문자 무시 정렬로 block을 만든다.
- `GetEnvironmentStringsW` 결과는 RAII로 해제한다.

### 2.4 명령줄 기록 분리

실제 실행에 사용하는 명령줄과 `process_result::masked_command_line`을 별도 값으로 분리했다. `S3-D5-CODE`가 기록용 값에만 마스킹을 적용해도 실행 인자가 바뀌지 않는다.

### 2.5 build 구성

`command_line_builder.*`, `process_output_pipeline.*`와 `win32_process_runner.*`를 `gitman_process`에 넣고 이 target이 `gitman_win32_platform`을 PRIVATE으로 링크한다.

계획 5장은 runner 파일을 `platform/win32`에 두라고만 정했고 target은 정하지 않았다. runner는 `validate_process_request`와 `build_windows_command_line` 심볼을 사용하므로 `gitman_win32_platform`에 넣으면 두 static library가 서로를 참조하는 순환이 생긴다. 파일 위치는 계획대로 `src/platform/win32/`에 두고 target만 `gitman_process`로 정했다.

## 6. 구현 중 검토 결과

- 처음에는 확인용 자식으로 `cmd.exe`를 사용했고 인자 왕복, 작업 디렉터리, 환경 확인이 모두 실패했다. 원인은 production code가 아니라 `cmd.exe`가 `CommandLineToArgvW` 규칙을 쓰지 않고 자체 따옴표 처리를 하기 때문이었다. 표준 `wmain` argv를 쓰는 자식으로 바꾸면 21개 항목이 모두 통과한다. 따라서 `S3-D2-TEST`의 도우미는 반드시 argv 기반 실행 파일이어야 하며 `cmd.exe`를 test 자식으로 쓰면 안 된다. 계획 8.1의 도우미 target 결정이 필요한 이유가 확인됐다.
- `InitializeProcThreadAttributeList`의 첫 호출은 `ERROR_INSUFFICIENT_BUFFER`로 실패하는 것이 정상 계약이므로 반환값이 아니라 필요한 크기로 성공을 판정한다.
- 재제출에서 `WaitForSingleObject` 실패 경로가 자식을 정리하고 `internal_error`를 보고하도록 고쳤다. `S3-D4-CODE`의 job object는 손자 프로세스까지 정리하므로 이 방어를 대체하지 않고 보강한다.
- 강제 분할 위치 계산은 처음에 상한 자체를 자르는 방식이어서 sequence 경계 보정이 동작하지 않았다. 구현 중 발견해 마지막 sequence가 미완결일 때만 그 시작으로 되돌리는 방식으로 바꿨고, 3 byte 문자를 두 번의 읽기로 나눠 보내는 확인 항목으로 검증했다.
- 내용 없는 진행 표시(`\r`만 연속으로 오는 경우)는 레코드를 만들지 않는다. 로그에 빈 줄이 쌓이는 것을 막고, `\n`으로 끝난 실제 빈 줄은 그대로 보존한다.

## 7. 알려진 중간 상태 제약

`S3-D2-CODE`만 적용한 현재 구현에는 다음 제약이 있다. 각 항목은 승인된 체크포인트 순서에 따라 뒤 구간에서 해소한다.

| 제약 | 해소 구간 |
| --- | --- |
| `process_text_encoding::active_code_page_fallback`을 지정해도 UTF-8 해석만 수행한다. | `S3-D3-CODE` |
| `request.timeout`과 취소 token이 무시되므로 자식이 끝날 때까지 무한 대기한다. | `S3-D4-CODE` |
| `masked_command_line`에 마스킹이 적용되지 않는다. | `S3-D5-CODE` |

이 구현을 실제 Git/SVN 명령에 연결하는 시점은 단계 4이므로 위 제약이 사용자 기능에 노출되지 않는다.
