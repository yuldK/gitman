# 단계 4 Git 및 SVN provider 최종 검증 기록

## 1. 검증 결론

단계 4의 모든 구현 구간, test 구간과 `S4-V1` 완료 조건을 충족했다. Git/SVN 도구 발견과 버전 확인, 비대화형 실행 정책, 로캘 독립 오류 분류, Git 로컬 및 remote-first 상태 판정, SVN 상태 판정, update 보호 정책과 실행, switch 후보 조회와 검증 및 실행이 구현되고 검증됐다.

`build/vs2022`를 삭제하고 다시 configure한 뒤 VS2022 Debug/Release와 VS2026 Debug의 전체 CTest가 각각 **393/393** 통과했다. VS2022 `/analyze`, aggregate format/style, Release install, 설치본 renderer smoke test와 PE 의존성 검사도 통과했다. 전체 suite 3회 반복과 7개 저장소 동시 조회 stress 3회에서 실패나 결과 흔들림이 없었다.

현재 상태는 **단계 4 최종 사용자 검수 대기**다. 사용자 승인 전에는 단계 5를 시작하지 않는다.

## 3. 구현 범위

### 3.1 도구 발견과 실행 정책

- 탐색 순서는 문서 `settings` 수동 지정 → `PATH` → 기본 설치 위치다. 지정 경로가 잘못되면 자동 탐색으로 물러서지 않고 `path_invalid`로 보고한다.
- 가용성은 `not_found`, `path_invalid`, `version_unreadable`, `too_old`, `available`이며 최소 버전은 Git 2.43.0, SVN 1.14.5다.
- **Git과 SVN이 모두 없는 환경을 1급 상태로 다룬다.** 도구 부재는 오류가 아니라 warning이며 카드는 목록에 남고 동작만 비활성화된다.
- 모든 Git 실행에 비대화형 환경 override 7종과 공통 인자 `-c core.quotepath=false -c gc.auto=0 -c color.ui=false --no-pager`를 붙인다. SVN은 `--non-interactive`다.
- 명령 부류별 timeout과 캡처 상한을 확정했다. 도구 조사 5초, 로컬 조회 30초, 원격 조회 120초, update 600초, switch 300초다.
- 로캘을 강제하지 않는다. 오류 분류는 SVN `E<숫자>` 코드, libcurl 및 OpenSSH 원문, HTTP 상태 번호, 프로세스 완료 사유 같은 로캘 독립 신호만 사용한다.

### 3.2 Git 상태

- `rev-parse` 배치 한 번으로 git dir, bare 여부, 작업 트리 안 여부와 최상위 경로를 얻는다. 실패하는 인자를 마지막에 두어 bare 저장소에서도 배치를 판정할 수 있다.
- `status --porcelain=v2 --branch`를 줄 단위로 읽는다. `-z`를 쓰지 않기로 확정했고 C 인용 경로는 `unquote_git_path`가 해제한다.
- 진행 중 작업과 `index.lock`은 표식 파일로 판정하며 filesystem 접근은 주입받은 `vcs_file_probe`로만 한다.
- 해석하지 못한 레코드가 있거나 branch 헤더가 없으면 작업 트리 상태를 `unknown`으로 둔다. 모르는 상태를 깨끗하다고 보고하지 않는다.
- 저장소 아님 판정은 번역되는 문장이 아니라 "정상 종료했는데 출력이 없다"는 구조적 신호로 한다.
- bare 저장소와 git dir 안을 가리키는 경로는 `unsupported_layout`이며 linked worktree는 추가 처리 없이 조회된다.

### 3.3 Git 최신 상태

- 선택 순서는 upstream → `preferred_remote` → `origin` → 유일한 remote다. 좁혀지지 않으면 **자동으로 고르지 않고** `remote_target_missing`으로 보고한다.
- upstream에서 remote 이름을 뗄 때 설정된 remote 중 가장 긴 접두사를 고른다. branch 이름에도 `/`가 들어갈 수 있기 때문이다.
- detached HEAD와 remote가 없는 저장소에서는 네트워크를 쓰지 않는다. 각각 `remote_target_missing`과 `local_only`다.
- remote branch 존재 확인은 `fetch` **뒤**에 한다. 한 번도 fetch하지 않은 저장소에서 원격에 있는 branch를 없다고 오판하지 않기 위해서다.
- fetch 실패는 `offline`, `authentication_required`, `error`로 나뉘며 직전 로컬 비교 값과 마지막 성공 원격 확인 시각은 지우지 않는다.

### 3.4 SVN 상태

- XML을 쓰지 않는다. `info --show-item`(값 한 줄), 비verbose `status`, `svnversion` 조합으로 필요한 값을 모두 얻으므로 새 dependency가 없다.
- `status` 경로는 앞 7칸을 상태 칸으로 보고 그 뒤 공백을 모두 건너뛴 지점부터 읽는다. 배포판별 패딩 차이에 강하다.
- mixed revision과 switched는 `svnversion`으로 판정하고, 없으면 조회를 막지 않고 값을 비운 채 `status`의 switched 칸으로 보조 판정한다.
- 원격 대비 상태는 현재 URL의 HEAD 리비전과 작업 복사본 리비전을 비교한다. SVN에 `ahead`와 `diverged`가 없어 `behind`와 `up_to_date`만 나온다.

### 3.5 update

- 순서는 **사전 검사 → 실행 → 사후 재조회**이며 사전 검사는 카드가 들고 있는 값이 아니라 지금 다시 조회한 상태로 한다.
- 차단 사유 우선순위는 도구 부재 → 저장소 아님 → 충돌 → 진행 중 작업 → `index.lock` → detached → dirty → diverged → 대상 없음이다. `working_tree_state::unknown`을 dirty와 함께 막는다.
- 명령은 `pull --ff-only`뿐이며 `--force`, `--rebase`, `--autostash`를 쓰지 않는다. remote와 branch를 명시하고 `--`로 끊는다.
- submodule 옵션이 켜지면 `submodule status --recursive`로 먼저 조사하고 충돌이나 커밋 불일치가 있으면 **parent pull을 시작하지 않는다.** `submodule update --init --recursive`는 parent가 성공한 경우에만 실행한다.
- `svn update`에 `--accept`를 주지 않아 충돌을 자동으로 해결하지 않는다.
- 성공과 실패 모두 사후 재조회를 수행하고 실행 성패와 조회 결과를 분리해 보고한다.

### 3.6 switch

- 검증 규칙 전체가 `application/switch_validation_service`의 순수 함수에 모여 있다. provider는 **승인 결과를 받은 뒤에만** 명령을 만든다.
- Git 후보는 `remote` → `fetch --prune <remote>` → `for-each-ref` 3개 명령으로 만든다. 심볼릭 ref를 제외하고, remote 후보를 먼저, local branch를 뒤에 둔다.
- 같은 branch 이름이 여러 remote에 있어도 합치지 않고 remote별 후보로 남긴다. remote 이름이 없는 대상은 `ambiguous_remote`로 거부한다.
- 새로 고치지 않은 remote의 후보는 `stale`이다. fetch가 실패해도 목록 자체는 만든다.
- 거부 사유 순서는 대상 없음 → remote 미지정 → 조회 불가 → 이미 대상 → 다른 worktree 사용 중 → 작업 트리 위험 → tracking 충돌 → 확인 요구다.
- tracking branch는 `switch_candidate::tracking_branch_confirmed`가 켜진 경우에만 만든다. 후보 조회는 이 값을 채우지 않는다.
- 실행은 `switch --no-guess`와 `switch --no-guess --create <local> --track`이며 `--discard-changes`, `--merge`, `--force`를 쓰지 않는다. 실행 직전에는 fetch하지 않는다.
- SVN 후보는 문서의 `svn_switch_targets`뿐이라 **process request를 하나도 만들지 않는다.** 검증은 허용 목록·형식·현재 위치·작업 트리를 네트워크보다 먼저 보고, 그 뒤에 대상 URL의 저장소 root와 UUID를 대조한다.

## 5. 동시 조회 stress

저장소 밖 임시 프로그램으로 실제 `git.exe`를 사용해 7개 저장소를 4개 스레드에서 동시에 조회했다. 확인 후 프로그램과 임시 저장소는 삭제했다.

저장소 구성은 동기, behind, ahead, dirty, detached, remote 없음과 존재하지 않는 경로다. 각 조회는 로컬 조회 → 원격 조회 → switch 후보 조회 세 가지를 모두 수행하므로 한 번에 Git 프로세스가 여러 개 만들어진다.

| 항목 | 1회 | 2회 | 3회 |
| --- | --- | --- | --- |
| 조회 | 56 | 56 | 56 |
| 기대값 불일치 | 0 | 0 | 0 |
| 수집한 switch 후보 합계 | 88 | 88 | 88 |
| 소요 시간 | 3,732 ms | 3,754 ms | 3,717 ms |
| 프로세스 handle | 71 | 71 | 71 |

세 번 모두 후보 합계가 같아 동시 실행에서도 결과가 결정적임을 확인했다. 시작 handle 70에서 71로 한 번 늘어난 뒤 3회 내내 유지되므로 실행별 handle 누수가 없다.

기대값은 저장소별 `availability`, 작업 트리 상태, `sync_state`와 최소 후보 수다. 존재하지 않는 경로에서는 후보가 비어 있어야 한다는 것도 함께 확인했다.

## 6. 단일 실행 파일 확인

Release install 결과는 `bin/gitman.exe` 한 파일이다.

| 항목 | 값 |
| --- | --- |
| 크기 | 6,255,616 byte |
| SHA-256 | `917C3734833395A89BF0FB815135EF65C4C7E3B36369DC690FA5D5EB68A9229F` |

`dumpbin /dependents` 결과는 `ole32.dll`, `SHELL32.dll`, `d3d12.dll`, `dxgi.dll`, `D3DCOMPILER_47.dll`, `dwmapi.dll`, `GDI32.dll`, `USER32.dll`, `KERNEL32.dll`뿐이다. VC runtime, Skia, ICU, Catch2와 프로젝트 DLL은 없다.

크기가 단계 3과 같은 이유는 실행 파일이 아직 `gitman_process`와 `gitman_vcs`를 링크하지 않기 때문이다. 두 library는 test로만 검증되며 실행 파일 조립은 단계 6의 app 조립에서 이뤄진다. SHA-256이 단계 3과 다른 것은 build 산출물의 timestamp 차이이며 코드 변화가 아니다.

## 8. 계획 대비 변경

| 변경 | 사유 |
| --- | --- |
| SVN에서 XML 대신 `--show-item`·`status`·`svnversion` 조합 사용 | `S4-P0` 검수 결정. XML 파서 dependency를 추가하지 않는다 |
| `-z` 미사용 확정 | 단계 3 파이프라인이 줄 끝 문자를 남기지 않아 NUL 구분 출력은 경계 정보를 잃는다. 줄 단위 출력에서 Git이 특수 경로를 인용하므로 더 안전하다 |
| remote branch 존재 확인을 `fetch` 뒤로 이동 | 한 번도 fetch하지 않은 저장소에서 원격 branch를 없다고 오판하지 않기 위해서다. 판정 결과는 같다 |
| `repository_availability::unsupported_layout` 추가 | bare 저장소와 git dir 안의 경로를 `not_a_repository`로 보고하면 카드에 잘못된 사유가 뜬다 |
| `status` 경로를 "앞 7칸 + 공백 건너뛰기"로 읽음 | 계획의 "고정 9칸"보다 배포판별 패딩 차이에 강하다 |
| submodule 사전 검사를 충돌과 커밋 불일치로 한정 | `git submodule status`가 submodule 내부 dirty를 보고하지 않는다. 내부 dirty 검사는 단계 6~7 |
| SVN switched·mixed를 값이 있을 때만 차단 | `svnversion`이 없어 판정할 수 없다는 이유로 update를 영영 막지 않기 위해서다 |
| `for-each-ref` 형식에 `%(symref)` 추가 | 심볼릭 ref를 이름 규칙이 아니라 값으로 제외하는 편이 정확하다 |
| "local-only branch"를 "remote 후보로 도달할 수 없는 local branch"로 해석 | 그대로 읽으면 upstream이 다른 remote를 가리키는 branch로 전환할 방법이 사라진다 |
| SVN 검증에서 로컬 판정을 네트워크보다 먼저 수행 | 어차피 실패할 전환에 원격을 건드릴 이유가 없다. `S4-D3`의 방향과 같다 |
| `switch_candidate::tracking_branch_confirmed`와 `switch_rejection::repository_unavailable` 추가 | 확인 여부를 실을 자리가 없으면 "확인 후 생성" 정책을 구현할 수 없고, 조회 불가 상태를 작업 트리 위험으로 보고하면 사유가 틀린다 |
| `win32_vcs_file_probe`를 `gitman_vcs` target에 배치 | `gitman_win32_platform`에 넣으면 static library 순환이 생긴다. 파일 위치는 계획대로 유지했다 |
| `is_absolute_windows_path`를 `domain/path_syntax`로 이동 | 문서 `settings` 검증과 프로세스 요청 검증이 같은 규칙을 쓰게 하기 위해서다 |
| test 도우미 이름을 `vcs_test_doubles`로 변경 | runner 대역과 file probe 대역을 함께 담기 때문이다 |

체크포인트 20개와 `CODE` / `TEST` / `FIX` 분할은 계획대로 유지했다.

## 9. 보류 및 후속 단계 경계

- **실제 `svn.exe` 실행 경로는 미검증이다.** 이 호스트에 SVN이 없어 명령 조립, 파서와 검증 규칙까지만 보장된다. 실제 환경에 붙일 때 확인할 것은 실행 경로 전부, `status`의 실제 칸 패딩, 원격 인증·연결 실패의 오류 코드, `info --show-item`이 값 외의 줄을 내는 배포판 여부다. 어긋나면 파서 한 곳을 고치고 `tests/fixtures/vcs/svn/`의 fixture를 실제 출력으로 교체하면 된다.
- SVN fixture는 실제 출력을 캡처할 수 없어 Apache Subversion 공식 문서의 출력 계약을 근거로 작성했다. 그 사실을 fixture 파일 주석에 남겼다.
- 실제 Git 통합 test는 로컬 경로 원격만 쓴다. 네트워크 전송과 실제 인증이 필요한 원격에서의 동작은 단계 8 범위다.
- `gitman_process`와 `gitman_vcs`는 아직 실행 파일에 링크되지 않는다. 조립은 단계 6이다.
- 탐색과 등록은 단계 5, 카드 UI와 로그 UI는 단계 6~7이다. Git worktree와 bare 저장소의 지원 범위도 단계 5에서 정한다.
- 카드별 lane, 저장소별 직렬화와 동시 실행 상한은 단계 6~7의 scheduler 범위다. 단계 4의 provider API는 호출 스레드를 점유하는 동기 API다.
- ADR-004의 범용 메시지 구조는 단계 6 구현 전 별도 사용자 설계 승인을 받아야 한다. 이 차단 조건은 그대로 유효하다.
- 환경설정 화면과 `settings` 편집 UX는 단계 6~7이다. 단계 4는 문서에서 provider까지의 데이터 경로만 만들었다.
- submodule 내부 dirty 검사와 submodule 표시 수준은 단계 6~7에서 다시 본다.
- `repository_change_result`에는 `has_errors()`가 없다. 조회 결과와의 이 비대칭은 단계 6에서 카드가 두 결과를 함께 다룰 때 다시 볼 항목이다.
- job object를 사용할 수 없는 환경에서는 손자 프로세스 정리가 보장되지 않는다(단계 3에서 남긴 항목).
- 단계 1의 caption 수동 검수 체크리스트 미확인 항목은 계속 보존한다.

## 11. 최종 검수 게이트

단계 4 자동 완료 조건은 충족했다. 사용자가 본 기록과 변경 내용을 최종 승인하기 전에는 단계 5 탐색 및 등록을 시작하지 않는다.
