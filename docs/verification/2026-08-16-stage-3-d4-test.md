# 단계 3 `S3-D4-TEST` 검증 기록 - 2026-08-16

## 1. 결과

timeout, 취소와 job object 트리 종료를 검증하는 test만 작성했다. 도우미에 `sleep`, `write-marker`, `spawn-child` 명령을 추가하고 Catch2 test 7개를 넣어 전체 CTest가 118개에서 125개가 됐다. production code는 변경하지 않았다.

VS2022 Debug/Release와 VS2026 Debug의 전체 CTest가 각각 125/125 통과했다. VS2022 `/analyze`는 경고 없이 통과했고 aggregate `gitman_format_check`도 통과했다. 타이밍에 의존하는 test 14개를 3회 반복 실행해 flakiness가 없음을 확인했다.

이번 구간에서 발견한 production 결함은 없다. 따라서 `S3-D4-FIX`는 사용자 확인 후 생략 대상이다.

## 2. 도우미 명령 추가

| 명령 | 동작 |
| --- | --- |
| `sleep <ms>` | `sleeping` 한 줄을 먼저 출력한 뒤 대기하고, 끝까지 살아 있으면 `woke`를 출력한다. 대기 전 출력이 있어야 timeout 이전 레코드 전달을 확인할 수 있다. |
| `write-marker <ms> <path>` | 지정 시간 뒤 marker 파일을 만든다. 손자 프로세스가 살아 있는지 판정하는 근거다. |
| `spawn-child <ms> <path>` | 자신을 `write-marker`로 다시 실행해 손자를 만들고 60초 대기한다. |

`spawn-child`가 만든 손자는 job에 상속되므로 트리 종료 대상이 된다.

## 3. 추가한 test (7개)

| test | 확인 내용 |
| --- | --- |
| timeout 종료 | 60초 자식에 400 ms timeout을 걸면 `timed_out`으로 끝나고 종료 코드가 비며 성공이 아니다. `process_timed_out` 진단이 남고 실행 시간이 요청 timeout 이상으로 측정되며, 제한 시간 이전에 나온 `sleeping` 레코드가 sink에 전달된다. |
| 실행 중 취소 | 별도 스레드가 300 ms 뒤 취소하면 `cancelled`로 끝나고 종료 코드가 비며 `process_cancelled` 진단이 남는다. |
| 사전 취소 | 이미 취소된 token은 프로세스를 시작하지 않는다. 레코드도 없고 명령줄도 기록되지 않는다. |
| 손자 종료 | 대조군과 종료군을 함께 검증한다. 손자가 200 ms 뒤 marker를 만들면 2초 timeout 안에 파일이 생기고, 손자가 2초 뒤 만들도록 하고 300 ms에 종료하면 3.5초를 더 기다려도 파일이 생기지 않는다. |
| timeout 이전 종료 | 30초 timeout을 건 빠른 자식은 `exited`와 종료 코드 7을 유지한다. |
| 미사용 취소 source | 취소하지 않은 source의 token은 정상 실행에 영향을 주지 않는다. |
| handle 누수 | 20회 반복 실행 전후의 프로세스 handle 수 차이가 8개 이하다. 실행마다 process, thread, pipe, job과 event handle을 열고 닫으므로 누수가 있으면 수십 개가 남는다. |

손자 종료 test에 대조군을 둔 이유는 "파일이 없다"는 단정만으로는 종료가 동작한 것인지 손자 생성이나 경로 자체가 실패한 것인지 구분할 수 없기 때문이다. 대조군이 먼저 파일 생성을 확인하므로 종료군의 부재가 의미를 갖는다.

시간 단정에는 여유 있는 상한을 사용했다. 자식이 60초를 자므로 20초 상한이면 종료가 동작하지 않을 때만 실패한다.

## 6. 발견한 결함

없다. 7개 test 모두 첫 실행에서 기대한 동작대로 통과했다.

작성 중 `std::thread`를 중괄호 초기화로 만들면서 lambda 본문이 여러 줄이 되어 source style 검사가 실패했다. lambda를 별도 변수로 분리해 해소했으며 test 논리는 바뀌지 않았다.
