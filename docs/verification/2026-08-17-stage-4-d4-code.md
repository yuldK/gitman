# 단계 4 `S4-D4-CODE` 검증 기록 - 2026-08-17

## 1. 결과

SVN 조회 경로를 구현했다. 명령 조립, `info --show-item`·비verbose `status`·`svnversion` 파서, 로컬 및 원격 상태 변환과 mixed revision·switched 판정이다.

update(`S4-D5`)와 switch(`S4-D6`)는 포함하지 않았다. 두 동작과 switch 후보 조회는 어떤 process request도 만들지 않는다.

VS2022 Debug/Release와 VS2026 Debug build 및 전체 CTest가 각각 274/274 통과했다. VS2022 `/analyze`가 경고 없이 통과했고 aggregate `gitman_format_check`, `gitman_source_style`, `gitman_assets_checksum`, `git diff --check`도 통과했다.

저장소 밖 임시 프로그램으로 115개 항목을 수동 확인하고 삭제했다. 5장에 결과를 기록한다.

## 2. 사용자 방침

2026-08-17 사용자 지시다. **SVN은 실제 개발 시점에 쓰지 않으며, 나중에 프로덕션 환경에 부품 끼워넣듯 최소 노력으로 적용할 수 있기만 하면 된다.**

이 방침을 다음과 같이 반영했다.

- 구조를 Git provider와 똑같이 맞췄다. 같은 계약(`repository_provider`), 같은 주입(`process_runner`, `vcs_file_probe`), 같은 실패 처리다. 나중에 실제로 붙일 때 읽어야 할 새 개념이 없다.
- 계획 4.6이 정한 명령 조합에서 벗어나지 않았다. 값 하나만 내는 `--show-item`, 비verbose `status`, `svnversion` 세 가지뿐이며 새 dependency도 없다.
- 실제 `svn.exe`가 있을 때만 동작하는 부분(원격 조회, 인증 실패 처리)은 코드로 연결만 하고 실측은 하지 않았다.
- SVN이 없는 환경이 정상 상태로 남는다. 도구 부재는 warning이고 카드가 목록에 남는다. 이 경로는 이 호스트에서 실제로 확인했다.

## 3. 구현 범위

### 3.1 새 파일

| 파일 | 내용 |
| --- | --- |
| `infrastructure/svn_command_builder.h/.cpp` | `info --show-item`, `status`, `svnversion`, 원격 리비전 요청 |
| `infrastructure/svn_output_parser.h/.cpp` | 값 한 줄, 고정 칸 `status`, `svnversion` 파서와 작업 트리 요약 |
| `infrastructure/svn_repository_provider.h/.cpp` | 로컬 및 원격 조회와 snapshot 변환 |

`src/CMakeLists.txt`의 `gitman_vcs`에 세 쌍을 추가했다. 새 외부 dependency는 없다.

### 3.2 명령

| 명령 | 부류 | 비고 |
| --- | --- | --- |
| `svn --non-interactive info --show-item <item>` | 로컬 조회 | `wc-root`, `relative-url`, `revision`, `repos-root-url`, `repos-uuid` 5개를 차례로 받는다 |
| `svn --non-interactive status` | 로컬 조회 | 대상을 주지 않아 작업 디렉터리 기준 상대 경로가 나온다 |
| `svnversion` | 로컬 조회 | **공통 인자를 붙이지 않는다** |
| `svn --non-interactive info --show-item revision <url>` | 원격 조회 | 네트워크를 쓰는 유일한 조회 |

`svnversion`은 `svn`과 다른 실행 파일이고 `--non-interactive`를 받지 않는다. 공통 인자를 그대로 붙이면 인자 오류로 실패하므로 이 명령만 요청을 직접 만든다. timeout, 캡처 상한과 인코딩 모드는 다른 명령과 같게 맞췄다.

항목마다 프로세스를 새로 띄우는 비용은 계획 4.6이 수용한 선택이다. 그 대신 사람이 읽는 `key: value` 목록을 파싱하지 않아 로캘과 무관하다.

### 3.3 `status` 칸 해석

계획은 "고정 9칸"으로 적었지만 구현은 **앞 7칸을 상태 칸으로 보고 그 뒤의 공백을 모두 건너뛴 지점부터를 경로로** 읽는다.

- SVN 1.7 이후의 상태 칸은 항목·속성·잠금·이력·switched·잠금 토큰·tree conflict 7개다. switched는 5번째(색인 4), tree conflict는 7번째(색인 6)다.
- 경로 시작 위치를 상수로 고정하면 배포판이 칸을 하나 더 붙일 때 경로가 잘린다. 공백을 건너뛰는 방식은 패딩이 7이든 8이든 9든 같은 결과를 낸다.
- 상태 칸이 모두 공백인 줄(`> moved from ...` 같은 부가 설명)은 항목이 아니므로 건너뛴다.

`--verbose`를 쓰지 않으므로 작성자 이름 컬럼이 없고, 경로에 공백이 있어도 경계가 흔들리지 않는다.

### 3.4 상태 매핑

| 판정 | 근거 |
| --- | --- |
| `conflicted` | 항목 칸 또는 속성 칸이 `C`이거나 tree conflict 칸이 `C` |
| `modified` | 항목 칸이 `M`/`A`/`D`/`R`/`!`/`~`이거나 속성 칸이 `M` |
| untracked | 항목 칸이 `?` |
| 세지 않음 | `I`(무시)와 `X`(외부 항목) |
| `has_mixed_revision` | `svnversion` 출력에 `:`가 있어 저·고 리비전이 다름 |
| `has_switched_subtree` | `svnversion`의 `S` 또는 `status`의 switched 칸 |
| `behind` | 원격 HEAD 리비전 > 작업 복사본 리비전. 차이를 `behind_count`에 담는다 |
| `up_to_date` | 두 리비전이 같음 |

SVN에는 Git의 `ahead`와 `diverged`가 없다. `ahead_count`는 항상 0이고 커밋하지 않은 로컬 변경은 `working_tree`로만 보고한다.

Git과 같이 해석하지 못한 줄이 있으면 작업 트리 상태를 `unknown`으로 둔다. 출력을 다 읽지 못한 작업 복사본을 깨끗하다고 보고하면 보호 정책이 무력해진다.

### 3.5 `svnversion`이 없을 때

`svnversion.exe`는 `svn.exe`와 같은 디렉터리에서 찾아 `S4-D1-CODE`가 `auxiliary_executable`에 담아 둔다. 없으면 조회를 막지 않고 다음과 같이 물러선다.

- `has_mixed_revision`은 값을 비운다(`std::optional`). 거짓과 미상을 구분한다.
- `has_switched_subtree`는 `status`의 switched 칸으로 보조 판정한다. 하나라도 있으면 참이다.
- 출력이 있는데 해석하지 못하면(`Unversioned directory` 등) warning 진단을 남기고 나머지 결과는 유지한다.

### 3.6 원격 조회

`query_remote`는 Git과 같이 받은 snapshot을 복사해 원격 값만 덮어쓴다. 실패해도 로컬 상태가 남는다.

현재 URL은 snapshot의 상대 URL과 저장소 루트를 이어 붙이지 않고 `info --show-item url`로 다시 물어본다. 규칙이 하나 적고 명시적 조회에서만 실행된다. 원격 조회는 명령 두 개(`url` 확인과 원격 `revision`)로 끝난다.

실패는 `S4-D1-CODE`의 분류기가 SVN `E<숫자>` 코드로 판정한다. 번역된 메시지에도 코드가 그대로 붙으므로 로캘에 의존하지 않는다.

## 7. 현재 알려진 결함과 미검증 범위

production 결함은 없다. 다만 다음은 **미검증으로 남는다**. 계획 8.4와 사용자 방침에 따른 의도된 범위다.

- 실제 `svn.exe`와 `svnversion.exe` 실행 경로 전부
- `status`의 실제 칸 패딩. 앞 7칸 뒤 공백을 건너뛰는 방식이라 패딩이 달라도 동작하도록 만들었지만 실측하지 않았다.
- 원격 조회의 실제 인증·연결 실패 메시지. 분류기 규칙은 `S4-D1-TEST`가 고정한 SVN 오류 코드에 기대고 있다.
- `info --show-item`이 값 외에 다른 줄을 내는 배포판이 있는지 여부. 파서는 첫 비어 있지 않은 줄을 값으로 삼는다.

실제 SVN 환경에 붙일 때 확인할 것은 이 네 가지다. 코드 변경 없이 확인만으로 끝날 가능성이 높고, 어긋나면 파서 한 곳만 고치면 된다.
