### 2.2 검증 서비스를 순수 함수로 둔 이유

`switch_validation_service`는 프로세스도 filesystem도 쓰지 않는다. 입력은 후보 목록, 대상과 검증 시점 상태뿐이고 출력은 코드와 한국어 메시지다.

이렇게 두면 **"검증에 실패하면 process request를 만들지 않는다"는 REQ-007 수용 기준이 provider 한 곳에서만 지켜지면 된다.** provider는 승인 결과를 받은 뒤에만 명령을 만들고, 그 밖의 모든 경로는 `executed == false`로 끝난다. 규칙 자체는 실제 저장소 없이 전수 확인할 수 있다.

진단은 프로젝트 문맥을 아는 provider가 만든다. 검증 결과는 코드와 메시지만 담는다.

### 2.3 Git 후보 조회

```text
1. git remote                       (새로 고칠 대상 선택과 remote/branch 분리에 필요)
2. git fetch --prune <remote>       (고르지 못하면 생략)
3. git for-each-ref ...             (remote tracking ref와 local branch를 한 번에)
```

정상 경로는 명령 3개다. 후보 목록 규칙은 다음과 같다.

| 규칙 | 내용 |
| --- | --- |
| 심볼릭 ref 제외 | `%(symref)` 값이 있으면 후보가 아니다. `refs/remotes/<remote>/HEAD`가 대표적이며 이름으로도 한 번 더 거른다 |
| remote 우선 정렬 | remote 후보를 먼저, local branch를 뒤에 둔다. 각 묶음 안은 `for-each-ref`의 ref 이름 정렬 그대로다 |
| 자동 병합 금지 | 같은 branch 이름이 여러 remote에 있어도 합치지 않고 remote별 후보로 남긴다 |
| local 후보 중복 제거 | remote 후보로 도달할 수 있는 local branch는 목록에 두 번 넣지 않는다. upstream이 그 remote와 **다른** local branch는 remote 후보로 도달할 수 없으므로 그대로 남는다 |
| stale 표시 | 이번 조회에서 새로 고치지 않은 remote의 후보는 `stale`이다. 하나라도 있으면 결과 전체도 `stale`이다 |

새로 고칠 remote는 `preferred_remote` → `origin` → 유일한 remote 순서로 고른다. 좁혀지지 않으면 **fetch하지 않고** 이미 받아 둔 tracking ref로 목록을 만든 뒤 `stale`로 알린다. upstream 규칙을 쓰지 않는 이유는 upstream이 현재 branch에 종속된 값이어서 "다른 branch로 옮기려는" 후보 조회의 기준으로 맞지 않기 때문이다.

fetch가 실패해도 목록은 만든다. 원격을 새로 고치지 못한 것과 후보를 전혀 알 수 없는 것은 사용자가 할 일이 다르다.

### 2.4 Git 검증 순서와 tracking branch 정책

| 순위 | 사유 | 조건 |
| --- | --- | --- |
| 1 | `target_not_found` | 대상이 비었거나 SVN 후보이거나 목록에 없다 |
| 2 | `ambiguous_remote` | remote 후보인데 remote 이름이 없다. 자동으로 고르지 않는다 |
| 3 | `repository_unavailable` | `availability != ready` |
| 4 | `already_on_target` | 전환해도 달라지는 것이 없다 |
| 5 | `target_in_use` | 다른 worktree가 그 local branch를 잡고 있다 |
| 6 | `working_tree_unsafe` | dirty, 충돌, **미상**, 진행 중 작업, `index.lock` |
| 7 | `tracking_branch_conflict` | 같은 이름 local branch가 **다른** remote를 추적한다 |
| 8 | `tracking_branch_confirmation_required` | 대응하는 local branch가 없고 사용자가 아직 확인하지 않았다 |

확인 요구를 가장 뒤에 둔다. 오류가 아니라 확인 요구이므로, 실제 차단 사유가 있으면 그것을 먼저 알려야 사용자가 할 일이 분명해진다.

`switch_candidate`에 `tracking_branch_confirmed`를 추가했다. 후보 조회는 이 값을 채우지 않고 dialog가 확인을 받은 뒤에만 켠다. 이 값이 꺼져 있으면 provider는 branch를 만들지 않고 되돌려 보낸다. 계약(`switch_to(project, target, token)`)에 별도 인자가 없어 확인 여부를 실을 자리가 필요했고, 이 값이 없으면 "확인 후 생성"과 "무조건 생성" 중 하나만 구현할 수 있다.

upstream이 **없는** local branch는 충돌로 보지 않는다. 이때 전환은 upstream을 건드리지 않고 그 branch로 옮기기만 하므로 사용자가 잃는 것이 없다. 계획 4.8의 "다른 upstream을 가짐"을 그대로 따른 판정이다.

### 2.5 Git 실행

```text
기존 local branch: git -c ... switch --no-guess -- <branch>
tracking 생성:     git -c ... switch --no-guess --create <local> --track -- <refs/remotes/…>
```

- `--no-guess`로 고르지 않은 remote branch로의 암묵 전환을 막는다. 호스트 Git 2.52.0에서 목록에 없는 이름이 `fatal: invalid reference`로 실패하는 것을 실측했다.
- `--discard-changes`, `--merge`, `--force`는 쓰지 않는다. 작업 트리에 변경이 남아 있으면 Git 자체가 거부한다.
- 두 명령 모두 `--`를 쓴다. `switch`가 `--`를 받아들이는 것과 `--track` 뒤의 완전한 ref가 옵션 값이 아니라 시작 지점으로 해석되는 것을 실측했다.
- 전환 부류라 timeout 300초, 캡처 상한 8 MiB다.

`switch_to`의 순서는 **재조회 → 재검증 → 실행 → 사후 재조회**다.

| 순서 | Git | SVN |
| --- | --- | --- |
| 1 | 대상 형식 확인(명령 없음) | 대상 형식 확인(명령 없음) |
| 2 | 도구 확인 | 도구 확인 |
| 3 | 로컬 조회 2개 | 로컬 조회 6~7개 |
| 4 | `remote`, `for-each-ref`, `worktree list` | 현재 URL 조회 |
| 5 | 재검증 | 허용 목록·형식·현재 위치·작업 트리 검증 |
| 6 | — | 대상 URL의 root와 UUID 조회(네트워크) |
| 7 | `switch` | `switch` |
| 8 | 로컬 재조회 2개 | 로컬 재조회 6~7개 |

정상 경로의 명령 수는 Git이 8개, SVN이 16개다. 5단계까지 중 하나라도 걸리면 **어떤 전환 명령도 만들지 않는다.**

실행 직전에는 **fetch하지 않는다.** 전환은 이미 받아 둔 ref로만 하며 `--no-guess`가 목록에 없던 대상으로의 암묵 전환을 막는다.

### 2.6 SVN

후보는 프로젝트 문서의 `svn_switch_targets`뿐이며 저장소 layout을 자동으로 가정하지 않는다. 따라서 **SVN 후보 조회는 process request를 하나도 만들지 않는다.** 형식을 해석할 수 없는 값은 후보에서 빼고 warning 진단으로 남긴다.

검증 순서는 허용 목록 → URL 형식 → 저장소 상태 → 현재 URL과 다름 → 작업 트리 안전 → **(여기서 처음 네트워크)** 대상 접근 가능 → root 일치 → UUID 일치다.

```text
svn --non-interactive switch <url>
```

`--ignore-ancestry`, `--force`와 `--accept`를 쓰지 않는다. 관계없는 저장소로의 전환과 자동 충돌 해결이 일어나지 않는다.

지원 scheme은 `http`, `https`, `svn`, `svn+ssh`, `file`이며 공백과 제어 문자가 든 값은 URL로 다루지 않는다.

## 3. 계획과 다른 점

1. `for-each-ref` 형식에 `%(symref)` 한 칸을 더했다. 계획 4.8은 `refs/remotes/<remote>/HEAD`를 제외하라고만 적었는데, 이름 규칙 대신 값으로 판정하는 편이 정확하다. 이름 검사도 함께 남겨 두었다.
2. 후보 조회에서 fetch할 remote를 `select_git_remote_target`이 아니라 별도 규칙(`preferred_remote` → `origin` → 유일)으로 고른다. 근거는 2.3이다.
3. 계획 4.8의 "local-only branch"를 "remote 후보로 도달할 수 없는 local branch"로 해석했다. 그대로 "remote에 같은 이름이 없는 branch"로 읽으면, upstream이 다른 remote를 가리키는 local branch가 목록에서 사라져 전환할 방법이 없어진다.
4. SVN 검증에서 로컬로 판정할 수 있는 것을 모두 네트워크보다 **먼저** 본다. 계획 4.8의 나열 순서는 접근 가능 여부가 앞이지만, 허용 목록 밖 URL이나 dirty 작업 복사본 때문에 어차피 실패할 전환에 네트워크를 쓸 이유가 없다. `S4-D3`에서 정한 "네트워크를 쓰기 전에 판정이 끝난다"와 같은 방향이다.
5. `svn switch`에 대상 경로 인자를 만들지 않는다. 계획은 `switch <url> <wc-path>`지만 작업 디렉터리가 이미 등록한 작업 복사본 루트이고, `S4-D5-CODE`의 `svn update`도 같은 방식이다. 같은 값을 두 번 싣지 않는다.
6. `switch_candidate::tracking_branch_confirmed`와 `switch_rejection::repository_unavailable`을 추가했다. 앞의 것은 2.4의 이유이고, 뒤의 것은 조회 자체가 안 되는 상태를 `working_tree_unsafe`로 보고하면 카드에 잘못된 사유가 뜨기 때문이다.
7. `svn info --show-item`에 URL을 주는 원격 조회를 `make_svn_remote_info_item_request`로 분리했다. 기존 함수는 로컬 조회 한도(30초)를 쓰는데 네트워크 조회에는 원격 한도(120초)가 맞다. 기존 `make_svn_remote_revision_request`는 새 함수를 호출하는 얇은 wrapper가 됐고 만들어 내는 요청은 그대로다.
