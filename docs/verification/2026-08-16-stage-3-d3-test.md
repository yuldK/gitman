### 2.3 `tests/win32_process_runner_tests.cpp` 추가분 (3개)

| test | 확인 내용 |
| --- | --- |
| fallback 복원 | 활성 code page로 인코딩한 `한글 상태` byte를 자식이 내면 fallback 모드에서 원문이 복원되고 대체 표시가 없다. transcode 표시는 활성 code page가 UTF-8인지에 따라 달라지므로 `GetACP()` 값으로 기대치를 계산한다. |
| fallback 미사용 | 기본 `utf8` 모드에서는 같은 byte가 U+FFFD로 대체되고 원문과 달라진다. 활성 code page가 UTF-8인 호스트에서는 의미가 없으므로 `WARN`으로 건너뛴다. |
| 정상 출력 보존 | fallback 모드에서도 유효한 UTF-8 출력은 변환 없이 그대로 전달된다. |

첫 두 test는 확인 문자열을 `WideCharToMultiByte(CP_ACP, ...)`로 runtime에 인코딩한다. 따라서 code page 949 호스트에서는 CP949 byte를, UTF-8 호스트에서는 UTF-8 byte를 쓰게 되어 두 환경에서 모두 유효한 검증이 된다.

## 6. test 작성 중 수정한 기대값

`win32_text_transcoder_tests.cpp`의 한국어 호스트 test에서 처음에는 "UTF-8 `한글` byte를 CP949로 해석하면 다른 문자가 된다"고 기대했고 단정이 실패했다.

실제 동작은 다음과 같으며 구현이 옳다.

- UTF-8 `한글`의 byte 순서(`ED 95 9C EA B8 80`)는 CP949에서 유효한 double byte sequence를 이루지 못한다.
- `MB_ERR_INVALID_CHARS`를 지정한 엄격 변환이라 결과를 만들지 않고 실패를 반환한다.
- 따라서 파이프라인은 U+FFFD 경로로 되돌아간다.

이 결과는 `S3-D3-CODE`의 판정 순서를 더 강하게 뒷받침한다. 유효한 UTF-8을 먼저 확인해 변환 자체를 건너뛰기 때문에 정상 출력이 code page 해석으로 훼손되지 않고, 설령 순서가 바뀌더라도 엄격 변환이 실패해 원문이 깨지지 않는다. 기대값을 실제 계약에 맞게 고치고 ASCII만 있는 UTF-8 문자열이 그대로 해석되는 단정을 추가했다.
