### 2.2 update의 순서

**사전 검사 → 실행 → 사후 재조회**다. 사전 검사는 카드가 들고 있는 값이 아니라 **지금 다시 조회한 상태**로 한다. 오래된 값으로 보호 정책을 판단하면 그 사이에 바뀐 저장소에서 명령이 나갈 수 있다.

| 순서 | Git | SVN |
| --- | --- | --- |
| 1 | 도구 확인 | 도구 확인 |
| 2 | 로컬 조회 | 로컬 조회 |
| 3 | 사전 검사 | 사전 검사 |
| 4 | `remote` 열거와 대상 선택 | — |
| 5 | (옵션) `submodule status --recursive`와 submodule 사전 검사 | — |
| 6 | `pull --ff-only` | `update` |
| 7 | (옵션, 성공 시에만) `submodule update --init --recursive` | — |
| 8 | 로컬 재조회 | 로컬 재조회 |

3~5단계 중 하나라도 걸리면 **어떤 변경 명령도 만들지 않는다**. `repository_change_result::executed`가 거짓인 것이 그 사실을 나타낸다.

성공과 실패 모두 8단계를 수행한다. 실행의 성공 여부(`succeeded`)와 조회 결과(`snapshot`)는 분리해 보고한다.

### 2.3 차단 사유와 우선순위

`evaluate_git_update_preflight`는 순수 함수다. 사유가 여럿이면 사용자가 먼저 해결해야 하는 것을 돌려준다.

| 순위 | 사유 | 조건 |
| --- | --- | --- |
| 1 | `tool_unavailable` | 도구 미설치 또는 버전 미달 (provider가 조회 전에 판정) |
| 2 | `repository_unavailable` | `availability != ready` |
| 3 | `working_tree_conflicted` | 작업 트리 충돌 |
| 4 | `operation_in_progress` | merge, rebase, cherry-pick, revert, bisect 중단 |
| 5 | `index_locked` | `index.lock` 존재 |
| 6 | `detached_head` | 비교할 branch가 없다 |
| 7 | `working_tree_dirty` | `modified` **와 `unknown`** |
| 8 | `diverged` | 양쪽에 커밋이 있다 |
| 9 | `no_remote_target` | remote가 없거나 대상을 자동으로 고를 수 없다 |

`working_tree_state::unknown`을 dirty와 함께 막는다. 모르는 상태에서 변경 명령을 실행하는 편이 더 위험하다는 `is_safe_for_change()`의 방향과 같다.

SVN은 `repository_unavailable` → `working_tree_conflicted` → `working_tree_dirty` → `switched_subtree` → `mixed_revision` 순이다.

### 2.4 SVN의 switched와 mixed를 값이 있을 때만 막는 이유

`has_switched_subtree`와 `has_mixed_revision`은 `std::optional<bool>`이다. `svnversion`이 없는 환경에서는 판정 자체가 불가능하다.

**값이 없으면 차단하지 않는다.** 판정할 수 없다는 이유로 update를 영영 막으면 도구 구성 문제 하나로 기능이 사라진다. 대신 조회가 이미 "svnversion 출력을 해석하지 못했다"는 warning을 남기므로 사용자는 상태를 알 수 있다. 작업 트리 상태와 달리 이 두 값은 "모르면 위험"이 아니라 "모르면 확인 불가"에 가깝다.

이 판단은 검수 대상이다. 더 안전한 쪽을 원하면 `value_or(false)`를 `value_or(true)`로 바꾸면 된다.

### 2.5 submodule 정책

`update_submodules`는 ADR-003대로 기본 off다.

| 옵션 | pull 인자 |
| --- | --- |
| off | `--recurse-submodules=no` |
| on | `--recurse-submodules=on-demand` |

on일 때는 pull 전에 `submodule status --recursive`로 상태를 조사한다.

| 표시 | 판정 |
| --- | --- |
| `U` 충돌 | **차단**(`submodule_unsafe`) |
| `+` 등록 커밋과 다른 커밋이 checkout됨 | **차단** |
| `-` 초기화되지 않음 | 차단하지 않는다. `--init`이 그대로 처리한다 |
| ` ` 정상 | 통과 |

하나라도 위험하면 **parent pull을 시작하지 않는다.** 부분적으로 갱신된 상태가 가장 되돌리기 어렵다. `submodule update --init --recursive`는 parent pull이 **성공한 경우에만** 실행한다.

조사한 submodule 목록은 결과 snapshot의 `submodules`에 담아 카드가 사유를 보여 줄 수 있게 한다.

### 2.6 명령 형태

```text
git -c ... pull --ff-only --recurse-submodules=no|on-demand -- <remote> <branch>
git -c ... submodule status --recursive
git -c ... submodule update --init --recursive
svn --non-interactive update
```

- `--ff-only`만 쓴다. `--force`, `--rebase`, `--autostash`는 쓰지 않는다. fast-forward가 불가능하면 merge를 만들지 않고 실패한다.
- remote와 branch를 명시하고 앞에 `--`를 둔다. 설정에 따라 다른 대상이 당겨지지 않고, `-`로 시작하는 이름이 인자로 해석되지 않는다. 호스트 Git 2.52.0으로 동작을 실측했다.
- `svn update`에 `--accept`를 주지 않는다. 충돌을 자동으로 해결하지 않고 그대로 남긴다.
- 세 변경 명령 모두 `update` 부류라 timeout 600초, 캡처 상한 32 MiB다. `submodule status`만 로컬 조회 부류다.

## 3. 계획과 다른 점

1. 계획 4.7은 submodule 사전 검사에 "dirty, conflict, detached"를 적었지만 `git submodule status`는 submodule 내부의 dirty를 보고하지 않는다. 이를 알려면 submodule마다 별도 명령을 돌려야 한다. 구현은 **충돌과 커밋 불일치만** 차단 사유로 쓰고, 미초기화는 위험으로 보지 않는다. 내부 dirty 검사는 단계 6~7이 카드 UI와 함께 다시 볼 항목이다.
2. SVN의 switched·mixed 차단을 값이 있을 때로 한정했다. 근거는 2.4다.
3. update가 사전 검사를 위해 로컬 조회를 스스로 수행한다. 계약(`update(project, options, token)`)에 snapshot 인자가 없고, 오래된 값으로 보호 정책을 판단하면 안 되기 때문이다. 명령 수가 늘지만 update는 사용자가 명시적으로 실행하는 동작이다.

| 저장소 | 결과 |
| --- | --- |
